## Philosophie

« Parlez. AZ s'occupe du reste. »

AZ IA comprend → réfléchit → utilise les API autorisées → confirme les actions importantes → accompagne l'utilisateur jusqu'à la fin de sa demande. Toute décision technique, fonctionnelle ou graphique doit rester compatible avec cette philosophie : aucun module ne doit être conçu comme une île isolée qu'AZ IA ne pourrait pas orchestrer plus tard.

## Rôle attendu

Agir en architecte logiciel senior avant d'écrire du code : analyser le besoin, analyser l'existant, identifier les impacts sur le reste de la plateforme, proposer une solution, développer, tester, documenter. Ne pas sauter d'étape pour un changement non-trivial — utiliser le mode plan de Claude Code pour ça plutôt que de coder directement.

## Architecture cible

```
Flutter UI → Application Layer (providers/state) → Services → Cloud Functions → Firestore/Storage
```

Note honnête sur l'état réel du code : une partie des écritures (ex. création de commandes livraison/courses/restaurant/pharmacie) se fait aujourd'hui directement depuis le client Flutter vers Firestore, sans Cloud Function intermédiaire — c'est l'état hérité, pas la cible. Toute logique métier **nouvelle** ou **sensible** (paiement, wallet, actions déclenchées par AZ IA, tout ce qui touche à la confiance/fraude) doit passer par une Cloud Function, jamais par une écriture Firestore directe côté client.

Il n'y a pas de produit "API Gateway" séparé devant les Cloud Functions — les Cloud Functions callable/HTTP **sont** la couche API. Ne pas introduire de gateway supplémentaire (Cloud Endpoints, Apigee, etc.) sans besoin concret : ça ajouterait une couche opérationnelle sans bénéfice tant que le trafic reste dans cette gamme.

## AZ IA — règles non négociables

AZ IA est un orchestrateur intelligent (raisonne, planifie, choisit le bon module, exécute via outils), pas un simple chatbot conversationnel — chaque nouvelle fonctionnalité de l'app doit être pensée en se demandant si/comment AZ IA pourrait aussi la piloter.

- AZ IA n'accède jamais directement à Firestore/Storage. Toute action passe par une Cloud Function (`functions/azia/`).
- Aucune action financière ou destructrice sans confirmation explicite de l'utilisateur, **validée côté serveur** (jamais une simple confirmation dans la conversation) — voir le mécanisme `ai_pending_actions` / `aiConfirmAction`. AZ IA ne valide jamais seul un paiement, un retrait, un remboursement ou une suppression.
- AZ IA ne doit jamais inventer d'information ; si une demande est incomplète (budget, adresse, destinataire manquant), il doit poser une question de clarification avant d'agir plutôt que de deviner.
- Contexte pris en compte : texte, voix, historique de conversation récent, préférences explicitement autorisées par l'utilisateur (opt-in — adresses favorites, moyens de paiement, langue, habitudes de commande ; modifiables/supprimables par l'utilisateur).
- Multilingue : le système actuel (`SYSTEM_PROMPT` français, `AppText` fr/en côté client) doit rester extensible à d'autres langues plus tard — ne pas coder en dur des hypothèses qui bloqueraient l'ajout d'une langue, mais ne pas construire l'infra multilingue avant qu'elle soit demandée.
- Administration : AZ IA peut à terme aider les admins (statistiques, détection d'anomalies, préparation de rapports, surveillance des opérations) mais ne prend jamais seul une décision administrative critique — ce périmètre n'est pas encore dans la feuille de route M0→M8 existante et doit y être ajouté explicitement (nouveau jalon) avant d'être implémenté.
- Immobilier : AZ IA ne signe jamais de contrat et ne prend aucune décision juridique — il recherche, compare, explique et organise une visite, rien de plus.
- Plan détaillé et état d'avancement du chantier AZ IA : voir la mémoire projet `project_az_ia_integration` (jalons M0→M8, M0 livré).
- **Précision (2026-07-02)** : la ligne « Contexte pris en compte » ci-dessus décrit le **contrat visé** établi dès le départ (Prompt 04), pas l'état actuel — la voix (M7) et les préférences opt-in (M8) ne sont pas encore construites. Voir Master Prompt 31 ci-dessous pour l'état réel précis.

**Master Prompt 32 (AZ IA vocale) — M7, jamais démarré jusqu'ici, mais moins risqué à lancer que ce prompt ne le suggère.** Contrairement aux prompts précédents (refus de reconstruire un système déjà en place), la voix n'existe **pas du tout** pour AZ IA aujourd'hui — pas un refus de reconstruction, une vraie question de démarrage de jalon. Vérifié précisément avant de répondre :
- **`speech_to_text` est déjà une dépendance ET déjà utilisée en production ailleurs dans l'app** — `lib/screens/client/courses_screen.dart` dicte déjà une liste de courses au micro (init, permissions, écoute, résultat). Ce n'est pas juste une dépendance dormante listée par anticipation : le plus dur (permissions plateforme, configuration native, comportement réel sur device) est déjà résolu et éprouvé — dé-risque sérieusement un démarrage de M7.
- **`flutter_tts` n'est pas encore ajouté** — seule vraie nouvelle dépendance nécessaire.
- **L'architecture déjà actée pour M7** (Prompt 04, validée avec l'utilisateur dès le lancement du chantier AZ IA) est volontairement mince : reconnaissance vocale → texte → **même contrat `azIaChat` que le chat texte, aucun changement serveur** → synthèse vocale de la réponse. C'est délibérément plus simple que la « couche d'abstraction multi-fournisseurs » demandée par ce prompt — `speech_to_text`/`flutter_tts` **sont** déjà des couches d'abstraction (au-dessus des moteurs vocaux natifs iOS/Android), en ajouter une troisième par-dessus serait la même sur-ingénierie déjà écartée au Prompt 29 (FeexPay) et au Prompt 31 (pipeline à 9 couches).
- **Multi-langue vocal ≠ multi-langue des réponses.** `speech_to_text` peut reconnaître plusieurs locales sans effort ; mais tant que `SYSTEM_PROMPT` reste français en dur (déjà noté Prompt 31), les réponses d'AZ IA resteront françaises même si la question est posée dans une autre langue — les deux chantiers sont liés mais distincts, ne pas supposer l'un résolu par l'autre.
- **Interruption/barge-in** : un vrai choix produit à trancher (arrêter le TTS en cours, écouter immédiatement, décider si l'interruption remplace ou complète le message en cours) — pas un détail d'implémentation, à concevoir explicitement.
- **Pilotage vocal de l'Administration** : la voix ne peut piloter que ce qui existe déjà côté outils texte — aucun outil IA d'administration n'existe (déjà acté), donc la voix n'ajoute aucune capacité ici, seulement une façon de parler aux outils déjà existants.

Point d'intégration déjà identifié : `lib/screens/ai/az_ia_chat_screen.dart` a déjà un champ texte unique appelant `provider.sendMessage(text)` — un bouton micro appellerait la même méthode avec le texte transcrit, sans toucher au contrat serveur.

**M7 livré (2026-07-02), scope volontairement minimal — pas la version étendue de ce prompt.** `flutter_tts` ajouté (`speech_to_text` l'était déjà). `AzIaProvider.sendMessage()` retourne désormais le texte de la réponse (succès ou message d'erreur) pour permettre à l'écran de le lire à voix haute — changement rétrocompatible, seul appelant existant mis à jour. `az_ia_chat_screen.dart` : bouton micro à côté du champ texte (même pattern `SpeechToText` que `courses_screen.dart`, résultat final auto-envoyé sans étape de confirmation supplémentaire, cohérent avec « Parlez. AZ s'occupe du reste. ») ; bascule volume dans l'AppBar (persistée via `SharedPreferences`, activée par défaut) pour activer/désactiver la lecture vocale des réponses. **Pas de vrai barge-in dans cette passe** — décision produit explicitement différée (voir plus haut) ; la seule protection actuelle est d'arrêter la synthèse en cours avant de commencer à écouter, pour que le micro ne capte pas la propre voix d'AZ IA. **Pas de multi-langue** — les réponses restent en français (system prompt inchangé), la reconnaissance vocale reste configurée en `fr_FR`. Trouvaille corrigée au passage : `NSSpeechRecognitionUsageDescription` manquait dans `ios/Runner/Info.plist` — requis séparément de `NSMicrophoneUsageDescription` par iOS pour `speech_to_text`, ce qui aurait aussi affecté la fonctionnalité vocale déjà existante de `courses_screen.dart` sur iOS, pas seulement AZ IA. Ajouté.

**Non testé sur appareil réel ou émulateur** — cet environnement ne permet pas d'exécuter l'app. Vérifié uniquement par `flutter analyze` (propre, mêmes 5 avertissements préexistants sans rapport) et lecture de code. Le flux réel (permissions micro/reconnaissance vocale au premier lancement, qualité de la synthèse vocale, comportement du bouton micro en conditions réelles) doit être testé manuellement sur un appareil avant mise en production — ne pas supposer que ça fonctionne tant que ce n'est pas vérifié en conditions réelles.

**Master Prompt 33 (mémoire/personnalisation/apprentissage AZ IA) — recoupe largement le jalon M8 (jamais démarré), avec une trouvaille de confidentialité plus sérieuse que prévu.** Les 4 mémoires demandées, état réel vérifié :
- **Mémoire de session : existe, mais ne se comporte pas comme une « mémoire de session ».** `ai_conversations/{uid}/messages` (`functions/azia/conversationStore.js`) charge les 40 derniers messages par `conversationId` — mais rien n'expire ni ne supprime jamais ces documents. Ce que ce prompt appelle « mémoire de session » (supprimée automatiquement après inactivité) est en réalité un historique permanent, jamais purgé.
- **Mémoire métier (commandes en cours, suivi, support) : pas une mémoire séparée, interrogée à la demande — un choix d'architecture délibéré, pas un gap.** L'outil `track_order` consulte l'état réel des commandes à chaque appel plutôt que de dupliquer ces données dans un cache mémoire — évite tout risque de désynchronisation (une commande annulée entre-temps ne serait jamais vue périmée). Rien à ajouter ici.
- **Mémoire utilisateur (favoris, moyen de paiement préféré, langue, habitudes) : n'existe pas.** Confirmé exhaustivement au Prompt 27 (aucune adresse favorite nulle part dans le code) et par la mémoire projet (`ai_preferences` never built, jalon M8).
- **Contexte dynamique (écran actuel, module, localisation ambiante, actions récentes) : n'existe pas.** Déjà confirmé précisément au Prompt 31 — seuls l'historique de conversation et le nouveau message sont transmis à Claude.
- **Apprentissage (horaires habituels, produits fréquents, adresses fréquentes) : n'existe pas** — dépend entièrement de la mémoire utilisateur ci-dessus, qui n'existe pas encore.

**Trouvaille la plus sérieuse de cet audit, distincte d'un simple gap de fonctionnalité : le « Principe fondamental » de ce prompt (l'utilisateur peut consulter/modifier/supprimer/désactiver sa mémoire) n'est respecté pour AUCUNE mémoire, y compris celle qui existe déjà.** Vérifié : `ai_conversations` n'est **jamais** lu directement par le client Flutter (recherche exhaustive : zéro résultat) — la seule façon de « voir » son historique est de faire défiler l'écran de chat lui-même, alimenté indirectement via `azIaChat`. Il n'existe aucun écran de gestion, aucun bouton « effacer mon historique », aucune façon de désactiver la mémorisation. Ce n'est pas juste « la mémoire utilisateur (M8) n'existe pas » — c'est que même la mémoire qui existe aujourd'hui échappe totalement au contrôle de son propriétaire, ce qui contredit directement le principe fondamental énoncé en tête de ce prompt.

Construire la mémoire utilisateur complète (favoris, préférences, apprentissage, personnalisation, chiffrement, analytics d'usage) est un chantier bien plus large que celui du Prompt 32 (voix) — contrairement à la voix, qui ne faisait que câbler des briques déjà existantes (`speech_to_text` déjà utilisé en production ailleurs), aucune des pièces de la mémoire utilisateur n'existe nulle part dans l'app aujourd'hui : nouvelle collection, nouvelles règles, nouvel écran de gestion, flux de consentement explicite, intégration dans le contexte des outils IA — un vrai chantier de conception, pas un assemblage. Pas construit silencieusement ici.

**Correctif ciblé livré (2026-07-02) : contrôle utilisateur sur la mémoire qui existe déjà.** Nouveau Cloud Function `clearAiHistory` (`functions/azia/index.js`, réutilise `clearHistory()` dans `conversationStore.js`) — supprime tout `ai_conversations/{uid}/messages` de l'appelant, par lots de 500 (boucle jusqu'à épuisement), rate-limité (5/heure), journalisé via `logAudit`. Câblé côté Flutter : `AzIaService.clearHistory()` → `AzIaProvider.clearHistory()` (vide aussi l'état local, réinitialise `conversationId`) → menu « ⋮ » de `az_ia_chat_screen.dart` avec dialogue de confirmation explicite (action irréversible). Ne couvre que la suppression manuelle à la demande — pas d'expiration automatique après inactivité (proposée mais non retenue cette passe), donc « mémoire de session » reste, pour l'instant, une mémoire qui ne s'efface que si l'utilisateur le demande explicitement. 3 tests unitaires (`functions/test/conversationStore.test.js`, `clearHistory()` seul — pas de test pour le CF `clearAiHistory` lui-même, cohérent avec l'absence de tests pour `azIaChat`, non mocké depuis le début du chantier IA).

**Master Prompt 31 (architecture du « cerveau » AZ IA) — la pile en 9 couches indépendantes demandée (Compréhension du langage → Détection d'intention → Analyse du contexte → Planification → Sélection des outils → Exécution → Validation → Réponse) n'est pas construite, et la construire ainsi serait une régression, pas une amélioration.** Ce prompt décrit l'architecture d'un chatbot pré-LLM (classificateur d'intention séparé, gestionnaire de dialogue à états, sélecteur d'outils codé à la main) — l'architecture réellement en place (`functions/azia/index.js`, boucle d'appel Claude avec tool-calling, plafond 6 tours) fait déjà tout ça, mais de façon **unifiée dans le raisonnement du modèle** plutôt qu'en modules séparés : c'est un choix délibéré et supérieur pour un agent piloté par un LLM moderne, pas un raccourci. Séparer ça en 9 couches codées à la main serait plus fragile (règles de classification d'intention à maintenir à la main) pour un gain nul. Vérifié directement, pas supposé :
- **Multi-intention dans un seul message : déjà natif.** `response.content.filter(b => b.type === 'tool_use')` peut contenir plusieurs blocs `tool_use` en un seul tour, tous exécutés avant de continuer — Claude sépare et exécute déjà plusieurs intentions dans une seule phrase sans classificateur séparé.
- **Personnalité, confirmation, « ne jamais inventer » : mot pour mot déjà dans `SYSTEM_PROMPT`** (`functions/azia/claudeClient.js`) — poli/professionnel/rapide/rassurant/concis, ne jamais deviner une info manquante (pose la question), confirmation serveur systématique avant toute action sensible. Rien à ajouter ici, déjà conforme.
- **Planification : implicite via le raisonnement multi-tours de Claude, pas un module « Planning Engine » séparé** — l'exemple du prompt (« achète 200f de tomates puis fais livrer à ma mère ») serait déjà géré par le même mécanisme qui gère aujourd'hui n'importe quelle demande multi-étapes : le modèle enchaîne les appels d'outils sur plusieurs tours (jusqu'à 6), guidé par le system prompt.
- **Outils : 15 réels** (`toolRegistry.js`) couvrant Livraison/Courses/Marketplace/Restaurants/Pharmacies/Immobilier/Wallet (partiel : solde+recharge, pas de paiement direct)/Support — correspond déjà à la plupart des catégories d'intention demandées. Administration en est absente, cohérent avec la position déjà actée (pas encore dans la feuille de route).
- **Sécurité (jamais Firestore direct, jamais de wallet/paiement/suppression sans confirmation serveur)** : le mécanisme `ai_pending_actions`/`aiConfirmAction` reste, après toute cette session d'audits, la partie la plus éprouvée du système — jamais la source d'un bug trouvé cette session (contrairement à plusieurs flux de paiement classiques côté Flutter).

Écarts réels, distincts de ce qui précède :
- **Contexte enrichi (écran actuel, localisation ambiante, préférences) : pas transmis à Claude aujourd'hui.** Seuls l'historique de conversation et le nouveau message sont envoyés — la localisation n'est utilisée que si un outil précis en a besoin comme paramètre explicite (fourni par le client), jamais poussée en contexte ambiant. Mémoire utilisateur/préférences/favoris : M8, pas construit (déjà su).
- **Mode vocal** : M7, pas construit (déjà su).
- **Multilingue runtime** : `SYSTEM_PROMPT` reste français en dur — extensible en principe (pas d'hypothèse bloquante codée en dur), mais aucun changement de langue à l'exécution n'existe.
- **Observabilité IA — construite (2026-07-02).** `azIaChat` (`functions/azia/index.js`) journalise désormais, à chaque appel (succès et échec), une entrée dans `request_logs` (même collection que le wrapper générique du Prompt 25, réutilisée plutôt que dupliquée) : `toolsUsed` (liste des outils réellement invoqués, lecture comprise), `turnCount` (nombre d'allers-retours Claude), `durationMs`, `inputTokens`/`outputTokens` (cumulés sur tous les appels Claude de la conversation, y compris l'appel de clôture si le plafond de tours est atteint), `hitTurnCap`. Écriture non-bloquante (jamais attendue avant de répondre à l'utilisateur). Ce n'est pas un simple branchement du wrapper générique `withObservability` (qui ne capture pas outils/tokens) : c'est une instrumentation dédiée écrite directement dans le handler, en plus du `logAudit()` déjà existant sur chaque outil d'écriture. **Non testé unitairement** — `azIaChat` n'avait déjà aucun test automatisé avant ce changement (nécessiterait de mocker tout le client Anthropic, hors du périmètre de ce correctif ponctuel) ; vérifié uniquement par lecture du code, `node -c`, et démarrage de l'émulateur Functions (aucune erreur au chargement). Cohérent avec l'honnêteté déjà actée section Tests & QA — ne pas prétendre que ce chemin est couvert par des tests tant que ça ne l'est pas.

## Architecture Flutter — organisation de lib/

État réel actuel : `screens/`, `services/`, `repositories/` (vide depuis le 2026-07-02, voir Prompt 41 ci-dessous), `providers/`, `widgets/`, `models/`, `utils/`, `theme/`, `l10n/`, `constants/`, `web/`, plus deux modules déjà organisés par feature — `marketplace/` et `ekbine/` (chacun avec ses propres `screens/services/providers/models`). C'est le modèle à suivre.

Cible pour tout **nouveau** module transverse (ex. `real_estate/`, futur `wallet/` si extrait) : un dossier top-level par feature, structuré comme `marketplace/`/`ekbine/`, plutôt que d'ajouter encore des fichiers dans `screens/client/` ou `screens/admin/`. Ne pas migrer le code existant (livraison, wallet, restaurant, pharmacie, admin — aujourd'hui répartis dans `screens/{client,driver,admin,restaurant,...}`) vers cette structure sans une décision explicite et un plan dédié : c'est un chantier à part, à fort impact, pas un sous-effet de bord d'une autre tâche.

Un fichier qui grossit trop (UI + logique métier mélangées) doit être découpé : widgets réutilisables dans `widgets/` ou le dossier du module, logique dans `services/`/`repositories/`, jamais de logique métier directement dans un `Widget.build()`.

**Master Prompt 41 (Clean Architecture v2, `core/`/`modules/{data,domain,application}`) — audit direct effectué, trouvaille la plus importante en tête : `lib/repositories/` existe déjà, mais est mort ET dangereux.**

- **Firestore appelé directement depuis un Widget : confirmé massif, pas un cas isolé.** Recherche exhaustive (`FirebaseFirestore.instance` dans `lib/`) : **121 fichiers**, grande majorité des `screens/*.dart` (pas des services/repositories). C'est la norme actuelle du projet, pas l'exception — cohérent avec l'absence quasi totale d'adoption de `lib/repositories/`.
- **`lib/repositories/` existe (3 fichiers, 345 lignes : `OrderRepository`, `UserRepository`, `WalletRepository`) mais a zéro appelant nulle part dans l'app** — vérifié par recherche exhaustive des noms de classe. Ce n'est pas juste inutilisé : en le lisant, ces trois classes sont **désynchronisées de la logique métier réelle et corrigée cette session**, et une au moins est un vrai risque si jamais réutilisée sans vérification :
  - **`WalletRepository.credit(userId, amount, ...)`/`.debit(...)` sont des méthodes génériques qui créditeraient/débiteraient le wallet de N'IMPORTE QUEL `userId` passé en paramètre, directement depuis une transaction Firestore côté client** — exactement le anti-pattern à l'origine des 3 bugs de paiement critiques trouvés et corrigés cette session (`payOrderFromWallet`/`cancelOrder`/`deliverOrder`, Boutique). Sous les règles de sécurité actuelles, un appel cross-user échouerait (`permission-denied`), donc ce n'est pas exploitable tel quel — mais si un futur développeur (humain ou IA) l'adopte en pensant bien faire (« réutiliser le repository existant »), il réintroduit silencieusement la même classe de bug déjà corrigée. **Ne jamais wire ce fichier sans le réécrire pour déléguer aux Cloud Functions existantes** (`payOrderFromWalletCF`, etc.).
  - **`OrderRepository.assignDriver()`** écrit `driverId`/`status` directement, sans transaction — court-circuiterait le verrouillage transactionnel du dispatch ajouté au Prompt 26 si jamais appelé. **`OrderRepository.cancel()`** ne rembourse rien — court-circuiterait `cancelOrderCF`.
  - **`UserRepository.deleteAccount()`** n'a pas l'étape de ré-authentification que la vraie implémentation (`profil_client.dart`) a — suppression de compte moins sûre que l'existant si jamais substituée.
- **Fichiers surdimensionnés confirmés, pas supposés** — les 10 plus gros fichiers de `lib/` dépassent tous 1000 lignes : `driver_dashboard.dart` (2024), `livraison_screen.dart` (1913), `service_providers_page.dart` (1708), `create_order.dart` (1631), `courses_screen.dart` (1531), `seller_dashboard.dart` (1508), `suivi_commande.dart` (1470), `boulangerie_order_page.dart` (1346), `admin_services_page.dart` (1277), `profil_client.dart` (1224) — tous mélangent UI, logique métier et accès Firestore direct.

**Ce que ce prompt lui-même autorise déjà, correctement, avant d'agir** : ses propres garde-fous (« ne jamais réécrire un module fonctionnel pour l'esthétique », « toute migration importante doit être justifiée, documentée, approuvée ») rejoignent exactement la position déjà actée plus haut (migration de l'existant = chantier à part, décision explicite requise).

**Décision (2026-07-02) : les 3 repositories morts/dangereux supprimés, le reste (nouvelle structure `core/`/`modules/`, migration des écrans existants) laissé de côté.** `lib/repositories/wallet_repository.dart`, `order_repository.dart` et `user_repository.dart` supprimés — confirmé zéro import, zéro appel nulle part dans l'app avant suppression (recherche exhaustive, y compris les chemins d'import). Les garder « corrigés mais toujours inutilisés » n'aurait rien réduit comme risque (le risque était qu'un futur développeur les découvre et les câble sans vérifier) ; les supprimer l'élimine complètement. `lib/repositories/` reste comme dossier vide, prêt à accueillir un futur repository réellement utilisé dès sa création (adoption prospective, pas de migration rétroactive des 121 fichiers qui appellent encore Firestore directement). `flutter analyze` toujours propre après suppression (mêmes 5 avertissements préexistants, aucun nouveau — confirme qu'aucun fichier ne les important réellement).

**Master Prompt 42 (Firestore Data Layer Enterprise) — audit direct effectué avant toute création de code, conformément à la règle explicite du prompt lui-même (« ne jamais créer des DataSources inutilisées sans justification », « migrer progressivement uniquement quand un écran est modifié »).**

- **Accès Firestore directs depuis les widgets : 121 fichiers confirmés (Prompt 41), pas re-mesuré ici** — même chiffre, même cause racine (`lib/repositories/` abandonné jusqu'à sa suppression au Prompt 41). ## Livraison — dispatch, tarification, preuve de livraison

État réel (audité, pas aspirationnel) :

- **Statuts** : `pending → broadcast/assigned → accepted → picked_up → delivered`, ou `cancelled` (avec `cancelReason`, ex. `no_driver_found`). Il n'existe pas d'états séparés "refusée"/"expirée" — un refus retombe en `pending`/`broadcast`, une expiration devient `cancelled`. Cet enum est validé par une state machine explicite dans `firestore.rules` (~lignes 238-263) et consommé partout (app livreur, admin, notifications, tracking). **Ne jamais renommer ni étendre ces statuts sans plan de migration dédié** — même si un vocabulaire plus riche (Créée/Recherche livreur/Livreur assigné/Acceptée/Colis récupéré/En livraison/Livrée/Terminée/Refusée/Expirée) est plus lisible fonctionnellement, il casserait tout ce qui compare des chaînes de statut aujourd'hui.
- **Dispatch — migré côté serveur (2026-07-01)** : distance uniquement (GeoHash, rayon 2 km par défaut) + **expansion progressive du rayon déjà implémentée** (`declineOrder()` dans `lib/services/firestore_service.dart`, repasse à 5 km si personne n'accepte). Le taux d'acceptation, le temps de réponse et l'historique de performance **ne sont pas** pris en compte dans le score d'attribution. La collection `driver_rankings` existe dans `firestore.rules` mais **n'est utilisée nulle part dans le code** — c'est un schéma mort, pas une fonctionnalité active. **Le dispatch n'est plus calculé côté client** : `FirestoreService.findNearestDriver()` délègue désormais entièrement au Cloud Function `dispatchOrderToDriver` (`functions/index.js`, réutilise `functions/dispatch.js` déjà utilisé par les outils AZ IA), qui relit lat/lng/budget depuis la commande elle-même côté serveur. Avant cette migration, le client lisait le `wallet` de TOUS les livreurs en ligne pour filtrer les candidats — c'était la justification historique de la règle `livreurs/{id}: allow read: if isAuth();` large ; cette justification n'existe plus, mais la règle elle-même n'a pas encore été resserrée (voir la section Sécurité pour l'état détaillé de ce chantier).
- **Tarification — point d'attention sécurité** : le prix est calculé **côté client uniquement** (`lib/services/tarif_service.dart`, constantes jour/nuit/distance/express codées en dur), sans validation serveur. **Master Prompt 26 (moteur de dispatch intelligent) — audit détaillé, connaissance directe (dispatch migré côté serveur dans cette même session) :**

- **Score d'attribution : 2 critères réels sur les 12 demandés.** `functions/dispatch.js` ne calcule pas de score — il filtre (isOnline/!isOnDelivery/isAvailable/!isSuspended/wallet≥commission/GPS<3min) puis trie par distance seule. - **Distance réelle vs vol d'oiseau — choix délibéré, pas un oubli.** `haversineMeters()` calcule une distance à vol d'oiseau, pas une distance/ETA routière (Google Directions). C'est cohérent avec l'historique déjà documenté (mémoire `project_maps_cost_audit` : facture Directions API de $87.92 déjà jugée trop élevée et réduite en juin 2026) — appeler Directions pour chaque candidat à chaque dispatch multiplierait ce coût par le nombre de livreurs en ligne à chaque commande. Si la distance routière est un jour voulue, elle doit se limiter aux N candidats les plus proches à vol d'oiseau (déjà filtrés), jamais à tous les livreurs en ligne.
- **Recherche progressive : réelle, mais partiellement orchestrée côté client.** Il existe bien 3 paliers (2 km initial → 5 km → 30 km, commentaire "P6" dans `customer_tracking_screen.dart`), mais deux mécanismes différents et non unifiés les déclenchent : (1) un refus explicite d'un livreur relance immédiatement `declineOrder()` avec `radiusKm: 5.0` (fixe, pas configurable) ; (2) l'absence de réponse déclenche un élargissement via des `Timer` **côté client** dans l'écran de suivi (30 s → 5 km, 60 s → 30 km) — si l'app cliente est fermée ou mise en arrière-plan, ces timers s'arrêtent et l'élargissement automatique n'a plus lieu. Ce n'est donc pas « entièrement exécuté côté serveur » comme l'exige ce prompt : le calcul/l'attribution le sont (CF `dispatchOrderToDriver`), mais l'**orchestration des relances** ne l'est pas.
- **Verrouillage — corrigé (2026-07-02).** `acceptOrder()` (acceptation par le livreur) était déjà protégée par une transaction Firestore avec vérification de statut. L'écriture d'attribution elle-même dans `dispatchOrder()` (`functions/dispatch.js`) ne l'était pas — écriture simple, sans transaction ni précondition de statut, pour l'assignation directe comme pour le passage en `broadcast`. Corrigé : les deux chemins passent désormais par une transaction qui relit le statut de la commande juste avant d'écrire et abandonne silencieusement (`{dispatched:false, mode:'already_assigned'}`) si elle n'est plus `pending` — même principe que `acceptOrder()`. Le marquage `pendingOrderId` sur les livreurs (cas broadcast) reste hors transaction (documents distincts, pas nécessaires à l'atomicité de la commande elle-même). Comportement observable inchangé dans le cas normal (aucun appel concurrent) ; 4 nouveaux tests couvrent le cas de course (`functions/test/dispatch.test.js`, 82 tests au total dans la suite).
- **Réattribution : 2 déclencheurs sur les 5 demandés.** Couverts : refus explicite, absence de réponse (timer client, voir ci-dessus). **Non couverts** : perte de connexion du livreur après attribution (aucune détection de heartbeat), suspension du livreur après attribution (aucune revérification), et timeout serveur d'une attribution/diffusion — aujourd'hui, si personne n'accepte, seul le scheduler générique `autoExpireOrders` (10 min, toutes commandes confondues) finit par **annuler et rembourser toute la commande**, plutôt que de relancer intelligemment la recherche.
- **`dispatch_metrics` existe et est réel, mais ne couvre qu'un seul angle.** Écrit par `autoExpireOrders` (pas par le dispatch lui-même) : uniquement `noDriverFoundCount` par date/zone/tranche de 3h. Déjà exploité par un petit widget dans `admin_security_dashboard.dart` (top 5 zones/créneaux en échec). Aucune métrique de succès (temps moyen d'attribution, distance moyenne, délai de réponse, taux d'annulation, efficacité de recherche) n'existe.
- **Priorités et livraison programmée : n'existent pas.** `express` n'est qu'un modificateur de **prix** dans `tarif_service.dart` — il n'influence ni le rayon initial ni l'ordre de diffusion. Aucun concept de commande programmée (heure future) n'existe dans le modèle de commande.
- **AZ IA « explique pourquoi ce livreur »** : impossible à construire honnêtement tant qu'il n'y a pas de score à expliquer — le dispatch actuel est un simple tri par distance, pas une décision multi-critères.
- **Tableau de bord admin dispatch en temps réel** : `admin_dashboard.dart` n'agrège que des compteurs globaux (commandes totales/livrées, livreurs total/en ligne) — pas de vue par commande en recherche, pas de répartition disponible/occupé en direct, pas de taux d'acceptation/refus par le moteur de dispatch spécifiquement.

Chacun de ces écarts (scoring multi-critères, respect des zones, distance routière, orchestration serveur des relances, réattribution sur perte de connexion/suspension, timeout de diffusion, analytics de dispatch, priorités, livraison programmée, explication IA, tableau de bord temps réel) est un chantier séparé et significatif — la plupart touchent le cœur du flux de livraison en production, à ne surtout pas construire silencieusement. - **Pas de vocabulaire de statut unifié** — le prompt demande un cycle unique (en attente/en cours/réussie/refusée/annulée/expirée/remboursée), mais la réalité a déjà **5+ vocabulaires différents et incohérents entre eux** : `wallet_transactions` top-level (pending/completed/error/cancelled/failed), sous-collections par utilisateur (champ `type` : recharge/withdrawal/refund/payment/purchase/sale/debit/earning — jamais le même jeu de valeurs d'un écran à l'autre), `withdrawal_requests` (pending/processing/sent/pending_manual), `ekbine_orders` et `orders` ont chacun leur propre enum de statut. - **Pas de moteur de commission unique et configurable** — seule la commission livreur (`config/commission`, paliers 100/200 FCFA) est pilotée par Firestore. Marketplace ne prélève **aucune commission** (le vendeur reçoit 100 % — la monétisation vient d'un abonnement/VIP vendeur, comme restaurants/boulangeries) — c'est une décision produit existante, pas un bug, et ça confirme que `create_marketplace_order` (M5) qui crédite 100 % au vendeur est correct. Ekbine a `fee=0` codé en dur (`ek_provider.dart`), cohérent avec la règle déjà connue « pas de commission Ekbine » (mémoire `project_ekbine_no_fee`) — donc pas un gap non plus, juste non centralisé dans `config/commission`.
- **Rapports financiers admin limités aux livreurs** — `admin_earnings.dart`/`admin_commissions_page.dart` existent mais ne couvrent que les commissions livreur ; aucun écran ne montre le chiffre d'affaires Marketplace/Restaurant/Pharmacie, aucun export CSV, aucun rapprochement.
- **Remboursement toujours total** — tous les chemins de remboursement trouvés (annulation, expiration, rate-limit dépassé) remboursent l'intégralité de `budget`/`totalPaid` ; aucun remboursement partiel n'existe.
- **Pas de suspension de compte client pour fraude** — les vendeurs (`subscriptionStatus`) et agents Ekbine (`isSuspended`) peuvent être suspendus, pas les clients (`clients/{uid}` n'a aucun champ de ce type).

Chacun de ces écarts (vocabulaire de statut, commission Marketplace/Ekbine centralisée, reporting financier multi-verticales, remboursement partiel, suspension client) est un chantier séparé à prioriser explicitement — ne pas les construire en réponse à ce prompt seul.

**Master Prompt 28 (« reconstruire entièrement » le Wallet en Grand Livre bancaire) — refusé en l'état, pour la raison la plus sérieuse de toute la session.** Ce prompt demande de remplacer le modèle de données actuel (`wallet` = un simple champ numérique sur le document du rôle, débité/crédité directement) par un Ledger comptable en partie double, immuable, avec comptes formels (client/livreur/vendeur/.../compte de réserve/compte technique), écritures liées débit↔crédit, machine à états à 10 statuts, UUID/signature par transaction, et une arborescence `wallet_core/ledger/transactions/payments/refunds/commissions/settlements/reports/security/audit`. Chacune des refontes déjà refusées cette session (renommage de schéma Prompt 21, réécriture des règles Prompt 22, gateway API Prompt 25, réorganisation Cloud Functions Prompt 23) portait sur de l'architecture ou de la sécurité ; celle-ci porterait sur **des soldes réels d'utilisateurs réels en production** — une migration mal exécutée ne casserait pas juste un flux, elle pourrait corrompre de l'argent. Aucune tentative de migration, même partielle, n'est faite ici.

État réel précis (au-delà de ce qui était déjà su du Prompt 10) :
- **Le système se comporte déjà, dans les faits, en partie double — sans que ce soit formalisé.** Chaque Cloud Function de paiement écrite cette session (`payOrderFromWalletCF`/`cancelOrderCF`/`deliverOrderCF`, Prompt 22 follow-up) débite toujours un compte et crédite toujours l'autre dans la **même** transaction Firestore, et journalise les deux côtés dans `wallet_transactions`. Ce qui manque, ce n'est pas l'équilibre (déjà garanti par construction), c'est la **preuve structurelle** : les deux écritures sont deux documents indépendants sans champ commun qui les relie explicitement (pas de `counterpartyTxId`/`ledgerEntryId` partagé) — un rapprochement doit aujourd'hui recomposer la paire par déduction (même `orderId`, même montant), pas par référence directe.
- **`wallet_transactions` est un journal, pas un Ledger.** Déjà append-only pour les non-admins (bonne nouvelle déjà notée) — mais un seul type/statut par ligne, pas d'origine/destination formelles, pas d'UUID normalisé (l'auto-ID Firestore est unique mais n'est pas structuré comme un UUID transactionnel), pas de "signature serveur".
- **Moteur de conciliation — construit (2026-07-02).** N'existait pas (recherche exhaustive de "reconciliation/réconciliation/discrepancy" : zéro résultat avant cette date). `functions/walletReconciliation.js` — diagnostic en lecture seule, tourne chaque lundi 4h (`walletReconciliationCheck`, `onSchedule`), recalcule le solde attendu de chaque compte à partir de `wallet_transactions` via des requêtes d'agrégation Firestore (`sum()`/`count()`, pas un téléchargement document par document — reste sobre même avec un historique volumineux) et compare au champ `wallet` réel. Portée volontairement limitée aux 6 collections qui partagent le schéma standard `wallet`+`wallet_transactions` (`clients`, `livreurs`, `sellers`, `restaurants`, `pharmacies`, `boulangeries`) — `ekbine_agents` utilise un schéma différent (`walletBalance`), explicitement hors périmètre plutôt que traité par approximation. Le vocabulaire `type` a été inventorié exhaustivement dans le code (10 valeurs connues : `recharge/refund/earning/sale/credit` = crédit, `withdrawal/payment/commission/debit/purchase` = débit) — toute transaction d'un type non reconnu est comptée séparément (`unclassifiedCount`) plutôt que devinée, pour ne jamais produire un faux positif basé sur une classification erronée. Écarts écrits dans `wallet_reconciliation_findings` (nouvelle collection, lecture super-admin uniquement) — seuls les comptes en écart y apparaissent, pas un snapshot complet à chaque run. 6 tests unitaires (`functions/test/walletReconciliation.test.js`).
- **AZ IA est déjà conforme à ce que demande ce prompt sur ce point précis** — consultation de solde/explication/préparation existent déjà (`get_wallet_balance`, outils de recharge), et aucune validation financière n'est jamais faite par AZ IA elle-même : tout passe par `ai_pending_actions`/`aiConfirmAction` avec confirmation serveur, règle non négociable depuis le début du projet. Rare point où ce prompt ne révèle aucun écart.
- **« Flutter ne modifie jamais directement soldes/écritures » n'est pas encore totalement vrai**, même après les correctifs de cette session : `acceptOrder()` (le livreur accepte, diminue son propre wallet) reste une transaction Firestore lancée directement par le client Flutter, tout comme `rechargeDriverWallet()`/`deductCommission()` côté admin — légitimes sous la règle de sécurité actuelle (owner qui diminue, ou admin), mais pas des Cloud Functions. Pas un bug (contrairement à ce qui a été trouvé et corrigé au Prompt 22 follow-up pour payOrderFromWallet/cancelOrder/deliverOrder), juste une exception à la règle absolue que ce prompt énonce.

**⚠️ Nouveau bug de paiement trouvé et corrigé (2026-07-02), même famille que les 3 déjà corrigés au Prompt 22 follow-up.** En construisant l'inventaire des types de `wallet_transactions` pour évaluer la conciliation, découverte que `lib/screens/client/boutique_page.dart` (module « Boutique AZ », relié depuis `client_map.dart`, avec son propre écran d'administration `admin_boutique_page.dart` — un flux réel, pas mort) débitait le wallet du client dans une transaction Firestore, créait la commande, PUIS tentait de créditer le vendeur boutique via `FirestoreService.creditSellerWallet()` — une écriture séparée, non transactionnelle, lancée directement par le client. La règle `sellers/{id}` (`isAdmin() || (isOwner(sellerId) && unchanged('wallet'))`) ne permet **jamais** à un client de créditer un vendeur : cette écriture échouait donc systématiquement, après que le débit client et la commande aient déjà réussi — paiement partiel silencieux (argent débité, vendeur jamais payé, commande de livraison jamais créée, client voit juste un message d'erreur générique). Corrigé en portant tout le flux wallet (débit client + crédit vendeur + décrément stock + création de la commande boutique, atomique) dans un nouveau Cloud Function `payBoutiqueOrderCF` (`functions/orderActions.js`, 7 tests), qui déclenche ensuite la course de livraison en best-effort — même comportement que l'original si cette dernière étape échoue. `boutique_page.dart` délègue désormais à ce CF pour le paiement wallet ; le chemin cash (non concerné, aucun crédit cross-user) reste inchangé. `FirestoreService.creditSellerWallet()` supprimé (plus aucun appelant).

Chacun des écarts structurels ci-dessus (liaison formelle des écritures, UUID/statuts normalisés, moteur de commission multi-critères, remboursement partiel, migration complète de tout paiement admin restant vers des Cloud Functions) est un chantier séparé, certains à fort risque sur des données financières réelles — à ne jamais construire silencieusement.

**Master Prompt 50 (2026-07-02, « Release Candidate Final Gate ») — synthèse finale, pas un nouvel audit de fond.** Compile l'ensemble des Prompts 01→50 dans `AUDIT_FINAL.md` (réécriture complète), avec 3 vérifications ciblées propres à ce prompt (documentées dans leurs sections respectives : `storage.rules` audité dans son ensemble pour la première fois, sécurité du démarrage de l'app vérifiée saine, suppression de compte vendeur/livreur sans avertissement de solde). **Verdict : READY PILOT** (pilote supervisé), pas prêt pour un lancement public non supervisé — voir `AUDIT_FINAL.md` section 13 pour le verdict complet, la liste exacte des risques restants et les actions obligatoires avant lancement public. Point le plus significatif de cette clôture : neuf bugs financiers critiques au total ont été trouvés et corrigés sur l'ensemble de la session (3 avant Prompt 40, 6 aux Prompts 46-49) — tous de la même famille (écriture Firestore cross-user bloquée par des règles correctement strictes, échouant silencieusement), confirmant que l'absence de tests d'intégration Flutter↔Firestore↔Cloud Functions était le facteur de risque le plus concret du projet, pas la conception des règles de sécurité elles-mêmes.

## Tests & QA — état réel, honnêteté sur ce chantier

Déjà confirmé (section Sécurité) : **aucun test automatisé n'existe** dans ce projet — `test/widget_test.dart` est un placeholder, `firebase-functions-test` est installée mais jamais utilisée, aucun test de règles Firestore. Honnêteté sur la méthode utilisée jusqu'ici pour le chantier AZ IA (M0-M5, mémoire `project_az_ia_integration`) : chaque étape a été vérifiée par chargement Node (`require()` + inspection des exports), démarrage de l'émulateur Firebase Functions, `flutter analyze`, et un test manuel unique du hachage de mot de passe — **pas de tests automatisés persistants**. Attente pragmatique à partir de maintenant (pas un programme QA complet, une ligne de base minimale) :
- Toute nouvelle Cloud Function contenant un calcul critique (commission, tarification, remboursement, hachage) devrait s'accompagner d'un test unitaire utilisant `firebase-functions-test` (déjà en dépendance, jamais utilisée) — surtout si demandé explicitement.
- Ne pas construire de pipeline CI/CD, de tests de charge ou de suite E2E sans décision explicite — hors de portée d'une réponse à une charte.
- Si l'utilisateur demande "teste ça", privilégier des tests ciblés sur la logique récemment touchée plutôt qu'une tentative de tout couvrir d'un coup.

**Première suite de tests créée (2026-07-01)** : `functions/test/*.test.js`, exécutable via `npm test` dans `functions/` (`node --test test/*.test.js` — runner natif Node, aucune dépendance ajoutée). Couvre `passwordHash.js` (hachage/vérification), `azia/dispatch.js` (calcul de commission, distance, logique complète d'attribution/broadcast), `azia/pendingActions.js` (création, confirmation, expiration, anti-replay, annulation), `realestate.js` (transitions de visite, permissions, agent approval) — 44 tests, tous verts. Technique clé : les fonctions `onCall(...)` de `firebase-functions/v2/https` exposent une méthode `.run(request)` intégrée au SDK, invocable directement dans un test sans émulateur ni `firebase-functions-test.wrap()` — pattern à réutiliser pour tester d'autres callables. `hashSecret`/`verifySecret` ont été extraites de `functions/index.js` vers `functions/passwordHash.js` pour rester testables sans initialiser Firebase Admin — même chemin à suivre pour toute future logique pure qu'on veut isoler du fichier principal.

**Tests de Firestore Rules ajoutés (2026-07-01) — écrits mais non exécutés.** `rules-tests/firestore.rules.test.js` (nouveau `package.json` racine, dépendance `@firebase/rules-unit-testing`) couvre les patterns les plus sensibles : protection du wallet (`clients`/`livreurs`), state machine `orders`, collections CF-only (`ai_conversations`, `ai_pending_actions`, `audit_logs`, `rate_limits`), séparation super-admin/sous-admin, verrou `pharmacies.password`, la seule règle publique du fichier (`config`). **Ces tests n'ont jamais tourné** : l'émulateur Firestore nécessite Java, absent de cette machine (`java -version` → command not found). Vérifié uniquement par `node -c` (syntaxe) et résolution du module — pas une exécution réelle. Ne pas supposer que ces tests passent tant qu'ils n'ont pas été lancés une fois sur une machine avec Java (ou en CI, où Java est disponible par défaut sur les runners GitHub Actions standard). Commande : `npm run test:rules` à la racine.

## DevOps, déploiement & exploitation — état réel

Baseline honnête, cohérente avec le constat déjà fait section Tests & QA (zéro automatisation) :

- **Un seul environnement Firebase** — `.firebaserc` ne référence qu'un projet (`az-express-clean`), pas de séparation dev/staging/prod, pas d'alias.
- **Aucune CI/CD** — pas de `.github/workflows/`, aucun pipeline. Le déploiement est manuel via `firebase deploy` / `firebase deploy --only functions`, sans vérification préalable, sans rollback outillé.
- **Pas de sauvegarde Firestore visible dans le code** — aucun export planifié (`gcloud firestore export`, Cloud Scheduler) référencé ; si une sauvegarde existe, elle est configurée hors dépôt (console GCP), donc invisible et non documentée ici.
- **Surveillance limitée à Crashlytics** (client) + `audit_logs`/`security_events` (déjà connus) — pas de Cloud Monitoring, pas d'APM externe, pas d'alerting automatique sur les pannes/latences.
- **Secrets via `functions/.env`** (gitignored) — pas de Firebase Secret Manager (`defineSecret`). Fonctionnel pour un seul mainteneur, mais rotation/partage d'équipe plus fragile qu'avec Secret Manager.

Construire l'infrastructure DevOps complète demandée par ce prompt (multi-environnements, pipeline CI/CD, monitoring/alerting, sauvegardes documentées, plan de reprise après incident) est un chantier à part entière, disproportionné en réponse à une charte — même limitation que pour les tests (section précédente). 1. **CI minimale** : un workflow GitHub Actions exécutant `flutter analyze` + `npm test` (déjà 26 tests, voir section Tests & QA) à chaque push — coût faible, attrape les régressions automatiquement à partir de maintenant.
2. **Sauvegardes Firestore planifiées** : fonctionnalité GCP native (export automatique quotidien), simple à activer, faible risque, comble un vrai trou (perte de données actuellement non couverte).

Ne pas construire le reste (multi-environnements, monitoring externe, plan de reprise formel) sans décision explicite.

**CI minimale créée (2026-07-01)** : `.github/workflows/ci.yml` — deux jobs, `flutter analyze` + `flutter test` d'un côté, `npm ci` + `npm test` (les 26 tests de `functions/`) de l'autre, déclenchés sur push/PR vers n'importe quelle branche. Les quatre commandes ont été vérifiées manuellement en local (toutes passent) avant écriture du fichier. **Ce dépôt n'a pas de remote GitHub configuré** (`git remote -v` vide) — le workflow est prêt mais ne s'exécutera qu'une fois le dépôt poussé vers GitHub avec Actions activé ; ne pas supposer que la CI tourne réellement tant que ce n'est pas confirmé.

**Master Prompt 38 (chaîne DevOps complète — environnements/CI-CD/observabilité/alerting/sauvegardes/reprise après incident) — quasi-doublon du Prompt 16, même verdict, réaffirmé après vérification.** Rien n'a changé sur le fond depuis le Prompt 16 : toujours un seul projet Firebase, toujours aucun remote git (`git remote -v` toujours vide, reconfirmé), toujours aucune sauvegarde planifiée visible dans le code, toujours pas de Secret Manager. Construire 6 environnements séparés, un pipeline blue/green + canary + rolling, un système d'alerte hiérarchisé et un plan de reprise formel avec post-mortems reste disproportionné pour un projet à mainteneur unique, sans changement de circonstance depuis le refus déjà motivé au Prompt 16 — mêmes raisons, pas re-développées ici.

## Sécurité

- Principe du moindre privilège partout (règles Firestore, rôles admin).
- Ne jamais faire confiance aux données envoyées par le client — validation et règles métier critiques côté serveur (Cloud Functions), pas côté Flutter.
- Réutiliser les helpers existants plutôt que les dupliquer : `checkRateLimit(uid, action, max, windowSeconds)` et `logAudit({...})` dans `functions/index.js`. Toute nouvelle Cloud Function sensible doit rate-limiter et journaliser de la même façon.
- Les collections `audit_logs`, `security_events`, `rate_limits`, `ai_conversations`, `ai_pending_actions` sont en écriture Cloud-Function-only (`allow write: if false` côté règles Firestore) — ne jamais assouplir ça pour un raccourci.
- Journalisation : toute action sensible (paiement, wallet, action IA) doit produire une entrée `audit_logs`.

**⚠️ Vulnérabilité concrète trouvée (pas un simple gap théorique) :** le mot de passe des pharmacies est stocké **en clair** dans `pharmacies/{id}.password` (écrit par `admin_pharmacies_page.dart`) et l'authentification pharmacie (`pharmacie_login.dart`) fait une comparaison directe en clair — ce n'est pas Firebase Auth, c'est une vérification Firestore custom. Quiconque peut lire ce document (bug de règles, accès console, etc.) récupère un mot de passe utilisable. **Ne pas corriger silencieusement** (migrer l'auth pharmacie casserait le login de vrais partenaires en prod si mal exécuté) — mais à traiter comme prioritaire dès que l'utilisateur valide une approche (hash côté Cloud Function a minima, migration vers Firebase Auth à terme).

**`livreurs/{id}.wallet` reste lisible par tout utilisateur authentifié — trouvaille documentée, non corrigée à ce jour (2026-07-01) :** `firestore.rules` a `allow read: if isAuth();` sur `livreurs/{livreurId}`, sans distinction de champ (Firestore ne permet pas une règle de lecture partielle par champ à l'intérieur d'un même document). La justification historique de cette règle large — le dispatch calculait côté client et devait lire le `wallet` de tous les livreurs en ligne pour filtrer les candidats — **n'existe plus** : le dispatch est désormais entièrement côté serveur (voir section Livraison, `dispatchOrderToDriver`). Restreindre correctement ce champ nécessiterait de le déplacer vers un emplacement séparé (sous-collection ou document dédié, à l'image de `pharmacie_credentials`) avec une règle `isOwner() || isAdmin() || isFleetOwnerOf()` — et de migrer ~10 sites de lecture/écriture restants qui touchent encore `livreurs.wallet` directement en client : les écrans propres au livreur (`driver_wallet.dart`, `driver_dashboard.dart` — lecture de son propre solde, légitime), 3 écrans admin (`admin_drivers_ranking.dart`, `admin_recharge_page.dart`, `drivers_page.dart`), `fleet_dashboard.dart` (un rôle « patron de flotte » distinct, modélisé par `fleet_owners/{id}` mais pas encore référencé dans la règle `livreurs`), et la diminution du propre wallet du livreur à l'acceptation d'une commande (`acceptOrder()`, déjà légitime et inchangée). Décision explicite (2026-07-01) : ne pas faire ce chantier maintenant — risque residuel accepté est une exposition de **visibilité de solde** (pas un risque de fonds : toute écriture cross-user reste bloquée par la règle `allow update`, et les 3 chemins qui la violaient ont été corrigés le même jour, voir section Livraison). À reprendre comme chantier dédié si priorisé explicitement.

**🆕 (Master Prompt 50, 2026-07-02) `storage.rules` audité dans son ensemble pour la première fois — même famille de risque que `livreurs.wallet` ci-dessus, sur des données d'identité cette fois.** `driver_photos/{driverId}`, `driver_selfies/{uid}`, `driver_id_photos/{uid}`, `fleet_selfies/{uid}`, `fleet_id_photos/{uid}` ont toutes `allow read: if isAuth();` — tout utilisateur authentifié (y compris anonyme) peut lire le selfie ou la pièce d'identité de n'importe quel livreur/flotte, à condition de connaître ou deviner l'UID exact du chemin (pas d'énumération triviale exposée par l'app elle-même). Pas corrigé — même arbitrage que `livreurs.wallet` (visibilité, pas vol de fonds ni d'écriture), à traiter ensemble si un chantier de resserrement des lectures est un jour ouvert. Le reste de `storage.rules` est solide : posture par défaut-refus (aucune règle catch-all permissive), validation systématique de type/taille sur chaque upload, écritures correctement scopées au propriétaire ou à l'admin partout ailleurs.

**🆕 (Master Prompt 50) Suppression de compte vendeur/livreur sans avertissement de solde actif.** `admin_sellers_page.dart`/`drivers_page.dart` suppriment le document sur simple confirmation (« sera supprimé, ne pourra plus se connecter »), sans vérifier ni afficher si `wallet > 0`. Action admin-only et déclenchée délibérément — pas un risque exploitable de l'extérieur — mais un vrai risque opérationnel si un admin supprime par erreur un compte avec un solde non nul (argent piégé dans un document supprimé, invisible à la conciliation). Pas corrigé, signalé pour un futur correctif ciblé (ajouter l'avertissement, pas bloquer la suppression).

Autres constats de l'audit sécurité/anti-fraude :
- **Authentification utilisateur régulier** : uniquement Firebase Anonymous Auth par défaut, avec un compte email/mot de passe optionnel (`client_auth_page.dart`) — pas de téléphone, Google ou Apple malgré la demande du prompt. - **Aucun test automatisé n'existe** — `test/widget_test.dart` est un placeholder, `firebase-functions-test` est une dépendance installée mais jamais utilisée, aucun test de règles Firestore (`@firebase/rules-unit-testing`). Le prompt demande explicitement "aucune mise en production sans validation des tests de sécurité" — c'est actuellement impossible à honorer littéralement ; à ne pas prétendre satisfait.
- App Check toujours absent (déjà signalé section Firebase) ; MFA au-delà du SMS admin (authenticator app, biométrie) n'existe pas ; pas de gestion de sessions actives/déconnexion à distance.

## API — conventions

Aujourd'hui, chaque Cloud Function retourne une forme différente (ex. `initiateFeexPayPayment` renvoie `{txId, paymentUrl, token, message}`, `ekClientConfirmOrder` renvoie `{success: true}`, `azIaChat` renvoie `{conversationId, reply}`) — il n'y a pas d'enveloppe de réponse unifiée `{success, error, message, data, code}`. **Ne pas retrofit les fonctions existantes** (ça casserait tous les appelants Flutter qui parsent déjà ces formes) : adopter une enveloppe cohérente uniquement pour les **nouvelles** Cloud Functions à partir de maintenant, sans renommer les champs de retour de l'existant. Pas de versionnement d'API (`/v1/`) aujourd'hui ; ne pas en introduire sans besoin concret (les callable functions sont déjà versionnées implicitement par déploiement).

## Firestore — schéma réel (ne jamais renommer en prod)

Le schéma effectivement en production diffère d'un schéma "manuel" idéal — c'est le schéma qui fait foi, pas une liste de collections théorique :
- Pas de collection `users` unique : le rôle est déterminé par la collection qui contient le document (`clients/{uid}`, `livreurs/{uid}`, `sellers/{uid}`, `restaurants/{uid}`, `pharmacies/{uid}`, `boulangeries/{uid}`, `ekbine_agents/{uid}`, `admins/{uid}` avec un champ `role: 'super'|'sub'`).
- Commandes livraison/courses/restaurant/pharmacie/marketplace partagent toutes la collection `orders` (polymorphe via `type`/`sellerType`) — pas de `shopping_orders` séparée.
- Ekbine a ses propres collections (`ekbine_orders`, `ekbine_agents`, `ekbine_chats/{orderId}/messages`).
- Le solde wallet est un champ (`wallet`) sur le document du rôle lui-même, pas une collection `wallet_accounts` séparée. `wallet_transactions` (top-level) + sous-collections par utilisateur existent déjà pour l'historique.
- `marketplace_products`, `support_tickets`, `audit_logs`, `security_events`, `rate_limits`, `zones_livraison`, `commissions` existent déjà et sont audités (voir mémoire projet `project_firestore_audit_fixes`, `project_security_audit`).
- Immobilier (`properties`) n'existe pas encore — voir le plan `real_estate_listings`/`real_estate_agents` déjà défini dans la mémoire `project_az_ia_integration`.

**Renommer/réorganiser ce schéma pour coller à un modèle "propre" théorique casserait toutes les Cloud Functions, règles Firestore, index et écrans existants — à ne jamais faire sans une décision explicite et un plan de migration dédié.** Les nouvelles collections doivent avoir un nom clair et cohérent avec l'existant, sans obligation de suivre une liste figée.

## RBAC

Le contrôle d'accès actuel fonctionne par appartenance à une collection plutôt que par un champ `role` unique + custom claims Firebase Auth (aucun `setCustomUserClaims` n'est utilisé dans le code aujourd'hui) : `clients`, `livreurs`, `sellers`, `restaurants`, `pharmacies`, `boulangeries`, `ekbine_agents`, `admins` (avec sous-rôle `super`/`sub`). Ça couvre déjà l'essentiel de la demande (Client/Livreur/Vendeur/Restaurant/Pharmacie/Agent E-Kbine/Admin/Super Admin). Les rôles "Support" (agent humain) et "Modérateur" ne sont pas encore modélisés — à créer seulement quand une fonctionnalité concrète en a besoin, pas par anticipation.

Précision (vérifiée lors de l'audit Administration) : les sous-admins ont en réalité un contrôle d'accès **par section**, pas juste un binaire super/sub — `admins/{uid}.permissions` est un tableau de clés de section (`livreurs`, `commandes`, `gains`, `restaurants`, etc., voir `admin_sub_admins_page.dart`). Ce n'est pas des rôles nommés hiérarchiques ("Responsable Livraison", "Comptable"...) comme demandé dans le prompt Administration, mais c'est un système de permissions granulaires déjà fonctionnel — plus proche de la demande qu'il n'y paraît. Ajouter des libellés de rôle par-dessus ce tableau de permissions existant serait un habillage léger, pas une refonte.

## Identité, Authentification, RBAC & KYC — état réel (2026-07-02)

Vue d'ensemble honnête : plusieurs pièces existent déjà et sont plus construites qu'on pourrait le croire (auth par téléphone réelle, KYC-lite livreur, RBAC granulaire déjà noté ci-dessus), mais aucune n'est unifiée en un système IAM cohérent — c'est un ensemble de mécanismes ad hoc par rôle, pas une couche d'identité centrale. Ne pas prétendre qu'un système IAM entreprise existe.

**Comptes réellement modélisés** : `clients`, `livreurs`, `sellers`, `restaurants`, `pharmacies`, `boulangeries`, `ekbine_agents`, `real_estate_agents` (M6), `fleet_owners`, `admins` (`super`/`sub`) — soit ~10 types réels. Les rôles Support Client, Modérateur, Comptable, Responsable Opérations n'existent pas (déjà acté section RBAC : à créer seulement sur besoin concret). « Propriétaire » du prompt est ambigu : `fleet_owners` existe déjà (patron de flotte livreurs) mais aucun concept de « propriétaire immobilier » distinct des `real_estate_agents` n'existe.

**Authentification par téléphone (OTP) — existe déjà, mais seulement pour la récupération de compte, pas pour la connexion primaire :** Firebase Phone Auth (`verifyPhoneNumber`/`PhoneAuthCredential`, `lib/services/auth_service.dart`) est réellement intégré et fonctionnel, câblé dans `forgot_password_page.dart` → `otp_verify_page.dart` (récupération de mot de passe) et dans `admin_otp_page.dart` (2FA admin après email/mot de passe) — mais aucun rôle ne s'authentifie *au quotidien* par téléphone+OTP comme le demande ce prompt ; les clients restent en Firebase Anonymous par défaut (avec upgrade email/mot de passe optionnel), les admins en email/mot de passe + OTP téléphone en second facteur. Pas de Google, pas d'Apple, pas de liaison multi-fournisseurs sur un même compte (`linkWithCredential` : zéro occurrence) — confirmé absent, pas juste non prioritaire.

**⚠️ Trouvaille concrète : deux mécanismes OTP admin parallèles, l'un mort.** `auth_service.dart` contient deux systèmes distincts pour la 2FA admin : (1) `generateAdminOtp()`/`verifyAdminOtp()` — code à 6 chiffres haché en SHA-256 et stocké dans `admins/{uid}.otpHash/otpExpiry/otpAttempts`, consommé par une branche de `otp_verify_page.dart` — mais `generateAdminOtp()` n'a **aucun appelant nulle part dans le code** : ce chemin ne peut jamais fonctionner en pratique (le hash n'est jamais généré, donc `verifyAdminOtp()` échoue toujours). (2) Le vrai chemin utilisé en production est entièrement différent : `admin_otp_page.dart` appelle `AuthService().sendPhoneOtp()`, un vrai SMS Firebase Phone Auth. Le système (1) est du code mort non détecté jusqu'ici — pas corrigé silencieusement (portée de cette passe = audit), mais à nettoyer ou supprimer lors d'un prochain passage sur l'auth admin.

**KYC — existe réellement, mais seulement pour les livreurs :** `driver_register.dart` impose un selfie obligatoire + une pièce d'identité optionnelle, uploadés vers Firebase Storage (`driver_selfies/{uid}/selfie.jpg`, `driver_id_photos/{uid}/id.jpg`), stockés comme `photoUrl`/`idPhotoUrl` sur le document `driver_requests`, et examinés par l'admin dans le cadre du flux d'approbation déjà existant. **Aucun autre type de partenaire n'a d'équivalent** — vérifié : `seller_register.dart`, `restaurant_register.dart`, `pharmacie_register.dart`, `boulangerie_register.dart` ne demandent aucun document, aucune photo, aucune vérification d'identité ; l'admin les approuve sur la seule base des informations texte saisies. Il n'existe pas non plus de statut KYC formalisé (Non commencé/En attente/Vérifié/Refusé/Expiré) — seulement le statut générique de la demande (`pending`/`approved`/`rejected`), qui mélange KYC et validation métier en un seul champ.

**Sessions & appareils de confiance : gap total, rien n'existe.** Aucune collection `sessions`, aucun enregistrement d'appareil/OS/version d'app/dernière activité, aucun écran « sessions actives », aucune détection de nouvel appareil. Seul `fcmToken` existe par utilisateur (pour les push) — un seul jeton par compte, écrasé à chaque nouvelle connexion sur un nouvel appareil (un signe indirect de changement d'appareil, mais pas exploité comme signal de sécurité aujourd'hui).

**Récupération de compte** : couverte partiellement — `sendEmailPasswordReset` (natif Firebase) pour les comptes email/mot de passe ; `resetAccountPassword` (Cloud Function) + `resetPasswordViaSms` (Dart) pour la réinitialisation cross-compte des types non-Firebase-natifs (ex. pharmacies, voir le système de hachage du Prompt 12), déclenchée après vérification OTP téléphone réelle. Les commentaires internes de `resetPasswordViaSms` (lignes 110-121) indiquent une incertitude assumée par l'auteur d'origine sur le cas où le compte lié au téléphone diffère du compte email cible — zone fragile, pas auditée en profondeur ici, à visiter si un bug de recovery remonte un jour.

**Changement de rôle** : ne correspond à aucun mécanisme unique dans l'architecture actuelle (RBAC par appartenance de collection, pas par champ `role`). Les analogues réels déjà existants et déjà admin-only : édition des permissions de sous-admin (`admin_sub_admins_page.dart`), rattachement/détachement d'un livreur à une flotte (`assignDriverToFleet`/`makeDriverIndependent`, `firestore_service.dart`). Le premier journalise désormais dans `audit_logs` (voir ci-dessous) ; le second (rattachement de flotte) ne le fait pas encore — pas dans le périmètre traité cette passe.

**Audit des événements d'identité — traité en partie (2026-07-02).** `audit_logs`/`logAudit()` existe et est déjà utilisé pour les actions sensibles (paiement, wallet, création de sous-admin, outils IA). Deux nouveaux Cloud Functions comblent une partie du gap : `logAuthEvent` (`functions/authEvents.js`) — appelé par le client juste après un `signIn` réussi (y compris après la 2FA admin, pas avant) ou juste avant un `signOut` volontaire — journalise `auth_login`/`auth_logout` avec le type de compte, câblé dans les 14 écrans de connexion/déconnexion réels (admin web+mobile avec gestion correcte du cas 2FA, fleet owner, boulangerie, restaurant, vendeur, livreur, client mobile+web, pharmacie). `logAdminAuditEvent` (admin actif uniquement, allowlist d'actions) journalise `permissions_changed`/`admin_activated`/`admin_deactivated`, câblé dans `admin_sub_admins_page.dart`. **Restent non couverts, décision explicite de ne pas les traiter cette passe** : échecs de connexion (nécessiterait un point d'entrée non-authentifié avec sa propre gestion anti-abus par IP, pas par uid — chantier à part), changements de mot de passe, révocations de session (aucune session à révoquer tant que le gap sessions/appareils ci-dessus n'est pas comblé), et le rattachement de flotte. Firebase Auth gère nativement la protection contre le brute-force (verrouillage temporaire après échecs répétés) — l'app ne rajoute pas sa propre limitation de tentatives de connexion par-dessus.

Chacune des trouvailles restantes (étendre le KYC-lite aux autres partenaires, nettoyer le code OTP mort, construire sessions/appareils de confiance, unifier récupération de compte, journaliser les échecs de connexion et le rattachement de flotte) est un chantier séparé à prioriser explicitement — pas construit silencieusement en réponse à cette charte.

## Intégrations déjà en place

MTN MoMo / Orange Money / Moov Money / Wave sont **déjà intégrés** via FeexPay comme agrégateur (`functions/index.js`, `feexpayOperatorCode()`) — pas besoin d'intégrations directes séparées sauf limite concrète de FeexPay constatée. Google Maps est intégré (voir mémoire `project_maps_cost_audit` pour le contexte coûts). AZ IA (Claude) est en cours d'intégration (voir `project_az_ia_integration`). Toute nouvelle intégration externe doit garder ses secrets côté `functions/.env` (jamais côté client), suivant le pattern déjà en place pour FeexPay.

**Master Prompt 29 (architecture de paiement universelle multi-fournisseurs) — refusé pour la même raison que les Prompts 23/25 : le prompt redemande une abstraction qui existe déjà, portée par un tiers.** FeexPay **est** déjà l'interface commune demandée — un seul appel API (`initiateFeexPayPayment`) route vers Orange/MTN/Moov/Wave selon `feexpayOperatorCode()`, un seul webhook (`feexPayWebhook`) reçoit les confirmations des quatre opérateurs sous un format unique. Construire une arborescence `payment_core/providers/{orange_money,mtn_momo,wave,cards}/` avec une intégration directe par opérateur dupliquerait ce que FeexPay fait déjà, et nécessiterait en plus des accords marchands séparés avec chaque opérateur (démarche commerciale/légale, pas juste du code) — aucun besoin concret constaté qui justifierait ça aujourd'hui.

Vérifié précisément (au-delà du simple « déjà intégré » déjà su) — le webhook `feexPayWebhook` est plus solide que ce que le prompt pourrait laisser supposer :
- **Authentifié** — par un secret dans l'URL (`?wh_secret=`), pas une signature HMAC (FeexPay ne la supporte pas, déjà noté au Prompt 03). Tentative avec un secret invalide → `security_events` sévérité `high`.
- **Idempotent** — vérifié explicitement (`tx.credited === true || tx.status === 'completed'` → retour immédiat "Déjà traité"), avec en prime une protection anti-rejeu par âge (webhook sur une transaction vieille de >24h → rejeté et journalisé).
- **Statuts internes indépendants du fournisseur** — les statuts FeexPay bruts (`SUCCESSFUL/SUCCESS/COMPLETED/PAID`, `FAILED/CANCELLED/CANCELED/REJECTED`) sont normalisés vers un vocabulaire interne (`completed`/`failed`/`cancelled`/`error`) avant d'être stockés — exactement ce que demande la section Statuts de ce prompt, déjà fait.
- **Journalisé** — `logAudit()` sur chaque crédit réussi, `logSecurityEvent()` sur les tentatives suspectes.
- **Crédit wallet atomique** — dans une transaction Firestore, cohérent avec tout le reste du système.

Écarts réels, distincts de ce qui précède :
- **Remboursement = crédit wallet interne, jamais un remboursement fournisseur.** Vérifié exhaustivement (aucun appel à une API de remboursement/annulation FeexPay nulle part dans `functions/`) : chaque chemin de remboursement du code (annulation, expiration, limite de commandes) crédite le champ `wallet` de l'utilisateur — l'argent ne repart jamais vers l'opérateur Mobile Money d'origine. C'est un choix d'architecture cohérent avec le fait que le Wallet AZ Express est le point de vérité financier de l'app, pas un défaut — mais ça veut dire que « remboursement total/partiel/automatique » de ce prompt ne s'applique qu'à la couche Wallet (déjà documenté section Wallet, Prompt 10/28), jamais à la couche paiement fournisseur.
- **Cartes bancaires** : aucune trace nulle part (recherche exhaustive "card/carte/visa/mastercard" dans `functions/index.js` : zéro résultat) — cohérent avec un marché ivoirien où le Mobile Money domine largement ; pas construit, pas de besoin concret identifié.
- **Conciliation fournisseur** : `walletReconciliationCheck` (Prompt 28, construit ce jour) compare le champ `wallet` à l'historique interne `wallet_transactions` — il ne compare **pas** avec les propres registres de FeexPay (leur API de consultation de statut/historique n'est jamais interrogée après coup). Un webhook perdu (FeexPay confirme un paiement, mais le webhook n'arrive jamais) resterait donc invisible à la conciliation actuelle. Ajouter cette troisième branche (appeler l'API FeexPay pour comparer) serait une extension naturelle de ce qui vient d'être construit, mais c'est une vraie nouvelle intégration externe (pas un ajustement mineur) — à prioriser explicitement, pas supposé inclus dans le travail du Prompt 28.

**Master Prompt 30 (moteur de notifications/FCM/événements de niveau entreprise) — refusé pour la reconstruction, vérifications précises apportées :**

Contrairement à la réorganisation en dossiers déjà refusée (Prompt 23, purement cosmétique), un vrai bus d'événements aurait un intérêt réel (ajouter un nouveau listener sans toucher le code existant) — mais le construire maintenant voudrait dire envelopper/refactorer 23 triggers déjà en production sur le chemin critique des notifications de commande. Pas fait silencieusement ; à prioriser explicitement si un jour voulu.
- **Priorités : un seul niveau existe réellement.** `sendToToken`/`sendToMultipleTokens` (`functions/index.js`) envoient systématiquement `android: {priority: 'high'}` — toutes les notifications sont "hautes", aucune notion de Critique/Haute/Normale/Faible différenciée. Petite chose à corriger si un jour utile, pas un problème aujourd'hui vu le volume.
- **Nettoyage des tokens invalides — corrigé (2026-07-02).** `sendToMultipleTokens` détectait déjà les tokens FCM invalides et les écrivait dans `invalid_fcm_tokens`, mais rien ne lisait jamais cette collection — le champ `fcmToken` resté invalide n'était jamais effacé du document utilisateur. `sendToToken` (envois à un seul destinataire) n'avait même pas cette détection — asymétrie avec `sendToMultipleTokens`. Corrigé : `sendToToken` détecte désormais aussi `registration-token-not-registered`/`invalid-registration-token` (même logique que `sendToMultipleTokens`) ; nouveau scheduler hebdomadaire `fcmTokenCleanupCheck` (`functions/fcmTokenCleanup.js`, lundi 5h — juste après `walletReconciliationCheck` à 4h et `cleanupExpiredRateLimits` à 3h) lit `invalid_fcm_tokens`, efface le champ `fcmToken` sur tout compte qui le détient encore (recherche par égalité sur les 10 collections connues portant ce champ : `clients/livreurs/sellers/restaurants/pharmacies/boulangeries/admins/ekbine_agents/fleet_owners/real_estate_agents`), puis retire l'entrée traitée. Borné à 400 entrées par exécution (marge sous la limite de 500 opérations par batch Firestore) — un éventuel surplus est repris la semaine suivante, idempotent. 6 tests unitaires (`functions/test/fcmTokenCleanup.test.js`).
- **Un seul appareil par utilisateur — déjà connu (Prompt 24), confirmé encore vrai.** `fcmToken` est un champ scalaire unique par compte (`NotificationService.saveToken()`), écrasé à chaque connexion sur un nouvel appareil — une session active sur un ancien appareil perd silencieusement les push. **Bonne nouvelle vérifiée en creusant** : le rafraîchissement de token EST bien géré (`_fcm.onTokenRefresh.listen(...)`, réécrit `fcmToken` si FCM le fait tourner en cours de session) — ce n'est donc que le multi-appareil qui manque, pas le rafraîchissement.
- **Templates/i18n côté notification serveur : n'existe pas.** Chaque appel à `sendToToken`/`sendToMultipleTokens` passe un titre/corps en dur, en français, construit à la volée dans chaque trigger — pas de couche de templates centralisée, pas de champ langue, pas de traduction côté serveur (contrairement à `AppText` fr/en déjà en place côté client pour l'UI).
- **AZ IA « expliquer/résumer une notification »** : n'existe pas comme outil AZ IA — aucun des 15 outils actuels (M0-M6) ne lit `clients/{uid}/notifications`. Chantier neuf, pas dans la feuille de route M0→M8 actuelle.
- **Analytics d'envoi (taux d'ouverture, taux de clic, délais, erreurs)** : n'existe pas en agrégat — chaque document notification n'a qu'un statut lu/non-lu, pas de confirmation de livraison ni de suivi de clic.
- **Synchronisation temps réel (commandes/wallet/marketplace/support)** : déjà satisfaite nativement par les écouteurs Firestore (`StreamBuilder`/`snapshots()`) utilisés partout dans l'app — ce n'est pas une couche construite à part, mais ça répond déjà fonctionnellement à la demande de ce prompt ; pas un gap.

Chacun des écarts restants (bus d'événements, priorités différenciées, multi-appareil, templates/i18n serveur, outils IA de notification, analytics d'envoi) est un chantier séparé à prioriser explicitement.

## Performance

Attention particulière à : nombre de lectures Firestore (pagination, requêtes ciblées plutôt que scans), taille et cache des images, consommation batterie (GPS/tracking en arrière-plan), temps de réponse perçu côté utilisateur, reconstructions de widgets inutiles (préférer `const`, découper les widgets plutôt que rebuild un arbre entier), lazy loading des listes longues (`ListView.builder`, pagination) plutôt que tout charger d'un coup.

État réel vérifié (Prompt 17) :

À corriger au cas par cas quand un écran est retouché, pas en un seul refactor global.
- **Pas de Firebase Performance Monitoring** — seuls Crashlytics/Analytics sont en place ; aucune trace personnalisée de temps de réponse.
- **Mode hors-ligne partiel** — la persistance Firestore est activée (`lib/main.dart`, cache 50 Mo), et un indicateur de connexion existe déjà (`customer_tracking_screen.dart`, bannière de connexion faible) — mais seulement sur cet écran ; les autres servent les données en cache sans jamais informer l'utilisateur qu'il est hors-ligne.
- **FCFA codé en dur partout** — `AppConfig.currency` existe mais n'est utilisé nulle part ; prix stockés en `int` brut sans métadonnée de devise. Toute évolution multi-devises demandée par ce prompt nécessiterait une abstraction qui n'existe pas encore.

**Optimisation AZ IA appliquée (2026-07-01)** : mise en cache de prompt côté Anthropic (`cache_control: {type:'ephemeral'}`) sur le system prompt (`SYSTEM_PROMPT_BLOCKS` dans `claudeClient.js`) et sur la dernière définition d'outil (`toolSchemas`, dans `azia/index.js`) — ce contenu est strictement identique à chaque appel `azIaChat`, donc coûteux à retraiter en entier à chaque tour de conversation. Réduit le coût/latence de chaque appel après le premier d'une session. Vérifié : suite de tests (26/26) toujours verte après ce changement, émulateur démarre proprement.

## Cartographie, GPS & Géolocalisation — état réel (Master Prompt 27, 2026-07-02)

Meilleure surprise que prévu sur plusieurs points ; deux gaps totaux confirmés (favoris, géoclôture) ; le reste recoupe des trouvailles déjà actées ailleurs (Livraison, Performance, Multi-pays, Sécurité) — cross-référencées ici plutôt que redupliquées.

**Itinéraires/ETA — bien plus solide qu'on pourrait le croire, MAIS scope limité au suivi actif.** `lib/services/google_routes_service.dart` (`GoogleRoutesService`) appelle réellement l'API Google Directions (distance/durée routières, `duration_in_traffic` si demandé), avec cache mémoire par grille 100 m/TTL 5 min et repli en ligne droite propre si l'API échoue — **jamais que du vol d'oiseau** pour ce chemin-là. Confirmé activement utilisé (pas du code mort) dans `lib/services/realtime_tracking_service.dart`, le service de suivi temps réel pendant une mission active : deux legs calculés (livreur→cible, cible→destination), recalcul throttlé à 120 s + déviation >200 m (cohérent avec la mémoire `project_maps_cost_audit`, qui avait déjà réduit ce throttle de 30 s à 120 s pour maîtriser les coûts — pas un gap, déjà optimisé). **Mais** cette précision routière ne couvre que le *suivi post-attribution* : le moteur de dispatch (`functions/dispatch.js`, voir Prompt 26 ci-dessus) continue de trier les candidats par distance à vol d'oiseau (`haversineMeters`) — c'est un choix assumé pour le coût (appeler Directions pour chaque livreur en ligne à chaque commande serait un multiplicateur de coût direct), pas un oubli, mais ça veut dire que « ne jamais utiliser uniquement le vol d'oiseau » n'est vrai qu'à partir du moment où un livreur est assigné, pas pendant la sélection elle-même.
**Trouvaille annexe — corrigée (2026-07-02).** `lib/services/eta_service.dart` (`ETAService`, distance à vol d'oiseau ÷ vitesse fixe 30 km/h) existait en parallèle de `GoogleRoutesService` sans aucun appelant nulle part dans le code — même famille que `generateAdminOtp()` (Prompt 24). Supprimé (`flutter analyze` toujours clean après suppression).

**Recherche d'adresse — déjà une architecture à 3 niveaux, cohérente avec le reste de l'app.** `lib/services/places_search_service.dart` cherche d'abord dans `places` (Firestore, local), puis Nominatim/OpenStreetMap (gratuit), puis Google Places API seulement en dernier recours si les deux premiers ne suffisent pas — avec cache Nominatim (TTL 5 min). Couvre déjà « recherche par adresse/quartier/ville/point d'intérêt » de façon raisonnable et économe.

**Lieux favoris (Maison/Travail/Famille/Boutique préférée) : gap total, confirmé par recherche exhaustive.** Aucune trace d'adresses enregistrées par utilisateur nulle part dans le code — ni modèle, ni écran, ni champ Firestore. **Zones de livraison — gestion géographique réelle, mais sans tarifs/horaires/restrictions par zone.** `admin_zones_page.dart` (déjà documenté section Administration) fait du CRUD complet avec capture GPS — mais confirmé qu'aucun champ tarif/horaire/restriction n'existe sur `zones_livraison`. **Accès aux positions GPS — même trouvaille que Sécurité/RBAC (Prompts 22/24), pas une nouvelle découverte.** Le suivi GPS d'un livreur n'est pas restreint « à une mission active ou aux admins » comme l'exige ce prompt : `livreurs/{id}: allow read: if isAuth();` reste large (voir section Sécurité, chantier explicitement laissé de côté le 2026-07-02).

Centralisée dans `MapsConfig.apiKey` (`lib/constants/app_constants.dart`), les 3 fichiers l'importent désormais au lieu de la redéfinir. **Ne change pas la posture de sécurité** — la clé reste embarquée côté client (exigence du SDK Maps lui-même) ; la restreindre par domaine/app/API reste un changement externe à faire côté Google Cloud Console, déjà noté dans la mémoire `project_maps_cost_audit`, toujours vrai, pas revérifié ici. ## Accessibilité & animations

Tailles de texte adaptables (passer par `AppTypography`, ne pas figer une taille), contraste suffisant, icônes compréhensibles sans dépendre uniquement de la couleur. Animations fluides mais jamais gratuites — si une animation n'aide pas la compréhension ou le feedback, ne pas l'ajouter ; toujours privilégier la fluidité perçue (60fps) à l'effet visuel.

## Évolutivité

Toute nouvelle fonctionnalité doit pouvoir être ajoutée sans casser les fonctionnalités existantes. Avant de modifier un modèle partagé (ex. `OrderModel`), vérifier tous les consommateurs existants (app livreur, admin, pricing, notifications) — préférer les extensions additives (nouveaux champs nullable) aux changements cassants.

## Multi-pays / multi-devises — vision long terme, pas un chantier actuel

Ce prompt est différent des autres : c'est un horizon à 10 ans, pas une fonctionnalité à construire maintenant. **L'application est aujourd'hui codée en dur pour la Côte d'Ivoire, et même plus précisément pour Abengourou** : `TarifService` (section Livraison) centre ses calculs sur des coordonnées GPS fixes (6.7273°N, -3.4961°E), `zones_livraison` n'a pas de couche pays/région au-dessus des villes/quartiers, FCFA est codé en dur partout (déjà signalé section Performance, `AppConfig.currency` inutilisé), et `AppText` fr/en (déjà connu) est la seule graine multilingue existante.

Construire une vraie architecture multi-pays (hiérarchie pays→région→ville→quartier administrable, devises indépendantes des calculs, fuseaux horaires, règles métier configurables par pays, paiements multi-prestataires par marché) toucherait quasiment toutes les collections, tous les calculs de prix, toutes les requêtes géo, toutes les notifications et tous les écrans admin — c'est une refonte pluriannuelle, pas une réponse à une charte. **Ne jamais prétendre que cette architecture existe ou est "prête" tant qu'elle n'a pas été réellement construite.**

Les éléments "vision future" du prompt (véhicules autonomes, drones, futurs canaux de paiement/communication) sont explicitement différés par le prompt lui-même ("si un jour disponibles") — aucune action requise, juste ne pas concevoir de nouveau code d'une façon qui les rendrait impossibles plus tard (ce qui est déjà couvert par les principes généraux ci-dessus : extensions additives, pas de couplage fort entre modules).

Si une réduction de portée est utile plus tard : la pièce la plus proche d'être actionnable est l'abstraction de devise déjà signalée section Performance (remplacer les `int` bruts + `' FCFA'` codé en dur par un formateur centralisé, même si un seul pays est supporté aujourd'hui) — c'est un prérequis à tout le reste, pas une fonctionnalité multi-pays en soi.

## Méthode de travail

1. Analyser le besoin.
2. Analyser l'existant (code, modèles de données, patterns déjà en place).
3. Identifier les impacts sur les autres modules.
4. Proposer la meilleure solution (mode plan pour tout changement non-trivial).
5. Développer.
6. Tester (analyze, compilation, émulateurs Firebase quand pertinent).
7. Documenter les décisions non-évidentes.
