## Courses — état réel et écart avec la vision "courses intelligentes"

Aujourd'hui : les commandes courses (`type='shopping'`) partagent le même `OrderModel`/collection `orders` que la livraison — une seule description libre + un seul champ `budget` consolidé, pas de liste d'articles structurée. Côté livreur, `lib/screens/driver/courses_disponibles.dart` affiche uniquement le `shoppingBudget` total — **aucune confirmation de prix par article, aucun envoi de photo, aucun signalement de changement de prix, aucune proposition/validation de remplacement n'existe nulle part dans le code aujourd'hui.** Une commande ne peut pas non plus mélanger plusieurs catégories (marché/boutique/pharmacie) — c'est un seul `type`/`sellerType` par commande. La notation existe déjà de façon générique (`lib/widgets/rating_dialog.dart`, utilisé dans `suivi_commande.dart`) et couvre déjà l'étape "évaluation" sans travail supplémentaire.

Le plan AZ IA déjà approuvé (mémoire `project_az_ia_integration`, jalon M4) prévoit d'ajouter un champ additif `items: [{name, budgetFcfa}]` sur les commandes courses pour permettre "100f de tomates, 200f de piment..." — **ça ne couvre pas** le workflow de négociation livreur↔client décrit ici (confirmation de prix réel par article, proposition de remplacement, validation client avant modification importante, photos). Ce workflow de négociation est un chantier plus large, pas encore planifié dans les jalons M0→M8 — à faire préciser/prioriser explicitement avant d'être construit, plutôt que de l'ajouter silencieusement à M4.
