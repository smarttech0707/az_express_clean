## Administration — état réel

Plus solide qu'on pourrait le croire sur l'authentification : `admin_login.dart` utilise Firebase email/mot de passe, avec **2FA SMS conditionnelle** (`admin_otp_page.dart`, vrai Firebase Phone Auth via `AuthService.sendPhoneOtp`) si un numéro est enregistré — sinon contournement avec avertissement. (Correction 2026-07-02, Prompt 24 : `AuthService.generateAdminOtp`/`verifyAdminOtp`, mentionnés ici auparavant, sont en réalité du code mort — `generateAdminOtp` n'a aucun appelant ; voir section Identité/RBAC/KYC pour le détail.) Gestion des zones de livraison déjà complète (`admin_zones_page.dart` : CRUD complet, capture GPS, activation/désactivation) sur `zones_livraison`. Voir aussi la section RBAC ci-dessus pour le système de permissions par section déjà en place.

Ne pas re-auditer ici ce qui est déjà documenté ailleurs dans ce fichier — écarts déjà identifiés et pertinents à l'Administration :
- **Pas de dashboard unifié multi-verticales** : `admin_dashboard.dart` n'agrège que livraison (commandes totales/livrées, livreurs total/en ligne) — rien sur Marketplace, Restaurant, Pharmacie, Immobilier dans un même écran ; ces métriques restent cloisonnées dans des écrans séparés (`admin_earnings.dart`, `admin_commissions_page.dart` pour les livreurs uniquement).
- Suspension client : voir section Wallet/Finance ci-dessus (n'existe pas).
- Réattribution/suspension livreur classique, modération Marketplace, reporting financier multi-verticales : voir sections Livraison, Marketplace, Wallet/Finance ci-dessus.
- AZ IA pour l'administration (stats, anomalies, rapports) : scope pas encore dans la feuille de route M0→M8, voir règles non négociables AZ IA ci-dessus.
- Pas de feature flags / config activable sans redéploiement : Remote Config n'est pas utilisé (voir section Firebase) — tarifs/commissions/catégories restent codés en dur là où déjà signalé (Livraison, Marketplace).

**Master Prompt 35 (Back Office Web « centre de commandement ») — trouvaille structurelle : le Back Office existe déjà en substance, mais scindé en deux implémentations séparées et déconnectées.** L'essentiel des fonctionnalités demandées par ce prompt (utilisateurs, livreurs, commandes, Marketplace, Immobilier, Restaurants, Pharmacies, Wallet, support, sécurité) existe déjà comme écrans Flutter réels et fonctionnels — audités un par un tout au long de cette session (Prompts 05 à 34). Le vrai écart n'est donc pas « rien n'existe », c'est architectural :
- **`lib/web/web_router.dart` n'expose qu'une seule route admin** (`/admin/dashboard`) menant à `WebAdminDashboard` (`lib/web/pages/admin/web_admin_dashboard.dart`, 758 lignes). Vérifié : ce fichier **n'importe aucun des écrans `admin_*.dart` mobiles** — c'est une implémentation autonome et bien plus réduite (5 onglets : Livreurs, Commerçants, Messages, SOS, Réinitialisation) construite indépendamment plutôt qu'en réutilisant/adaptant les dizaines d'écrans admin déjà riches côté mobile (zones, commandes, stats géo, classement livreurs, sous-admins, sécurité, gains, commissions, modération...).
- **Deux back-offices parallèles et déconnectés, même famille de trouvaille que les deux systèmes Immobilier (M6) ou les 5+ vocabulaires de statut wallet (Prompt 10)** : l'app mobile (Flutter, cross-platform par nature) a un back office riche mais pensé pour un écran de téléphone ; le web a un back office pensé pour navigateur mais volontairement limité à une poignée de fonctions. Les unifier (rendre les écrans admin mobiles réellement responsive et les exposer aussi sur `/admin/...`, ou l'inverse) serait un vrai chantier UX/architecture — pas une simple recompilation, ces écrans ont été conçus avec des contraintes mobiles (bottom sheets, largeur fixe, navigation par `Navigator.push`) qui ne transposent pas telles quelles à un layout desktop large. Pas fait silencieusement.
- **Écarts réels non couverts par aucune des deux implémentations** : pas de compteur d'utilisateurs connectés en temps réel, pas de moteur de recherche dans les journaux d'audit (`admin_security_dashboard.dart` n'affiche qu'un widget des 5 pires zones/créneaux de dispatch — pas une recherche/filtre sur `audit_logs` par action/utilisateur/période malgré l'index `(action,createdAt)` déjà existant et prêt à l'emploi), pas de feature flags (déjà su), pas d'historique des changements de paramètres (`config/commission` n'a pas de journal de versions).

Chacun de ces écarts (unification des deux back-offices, compteur temps réel, historique de paramètres) est un chantier séparé et significatif — le moteur de recherche dans `audit_logs` est la pièce la plus proche d'un ajout ciblé et sûr (données déjà indexées, juste une UI de recherche/filtre à construire), le reste nécessite de vraies décisions de produit/architecture.

**Master Prompt 57 (2026-07-03, « Admin Back Office Consolidation Audit ») — audit complet des deux admins avant toute décision ; verdict : complémentaires, pas dupliqués, avec deux bugs réels trouvés et corrigés (un gap de sécurité mineur, une régression fonctionnelle majeure côté site public).**

**Phase 1 (inventaire, qui peut faire quoi) :**
- **Admin Flutter mobile** (33 écrans `lib/screens/admin/*.dart`, point d'entrée `admin_dashboard.dart`) reste, sans exception trouvée, le seul endroit où sont possibles : valider un livreur (`driver_requests_page.dart`), gérer les commandes (`admin_orders.dart`), gérer les paiements/wallet/commissions (`admin_recharge_page.dart`, `admin_commissions_page.dart`, `admin_earnings.dart`), gérer la Boutique (`admin_boutique_page.dart`), approuver/gérer restaurants/pharmacies/boulangeries/vendeurs (`admin_restaurant_requests_page.dart` et consorts), gérer les zones, le dispatch, les sous-admins, la sécurité. **Suspendre un utilisateur** : seuls les agents Ekbine peuvent l'être (`admin_ekbine_page.dart`, déjà documenté section Wallet/Livraison) — aucun autre rôle n'a de suspension, mobile ou web. **Gérer l'Immobilier** : confirmé qu'**aucun des deux admins** n'a d'écran pour ça — `approveRealEstateAgentRequest` (Prompt M6) reste une Cloud Function sans UI Flutter nulle part, appelable seulement depuis la console/un script. Ce n'est donc pas un écart mobile-vs-web, c'est un gap partagé par les deux.
- **Admin Web** (`lib/web/pages/admin/web_admin_dashboard.dart`, 758 lignes, seule route `/admin/dashboard`) : confirmé, en relisant le fichier en entier, qu'il **n'importe aucun des 33 écrans `admin_*.dart` mobiles** et ne touche à AUCUNE des collections opérationnelles ci-dessus (`orders`, `wallet` d'aucun rôle, `commissions`, `zones_livraison`, `real_estate_*`, `sellers`, `restaurants`, `pharmacies`, etc. — zéro référence trouvée). Son périmètre réel, entièrement distinct : 5 onglets sur seulement 5 collections — `driver_applications`, `partner_applications`, `contact_messages`, `sos_alerts`, `password_reset_requests`.
- **Trouvaille clé de la Phase 1, qui change la nature du diagnostic : `driver_applications`/`partner_applications`/`contact_messages` ne sont PAS les mêmes collections que le pipeline d'approbation mobile.** `driver_applications` (rempli par `lib/web/pages/drivers_page.dart`, le site vitrine public) est un formulaire de **lead pré-compte** (nom/téléphone/ville/véhicule, suivi manuel WhatsApp) — totalement distinct de `driver_requests` (inscription in-app réelle avec compte Firebase Auth, approuvée via `driver_requests_page.dart`, qui crée le document `livreurs/{uid}`). Même distinction pour `partner_applications` vs `seller_requests`/`restaurant_requests`/`pharmacie_requests`/`boulangerie_requests`. **Aucun chevauchement de données** : ces 3 collections web n'existent nulle part côté mobile, et vice versa — le Web Admin gère des prospects marketing pré-compte, le Mobile Admin gère le cycle de vie réel des comptes/commandes/paiements. C'est la même distinction de rôle déjà établie pour Immobilier au Prompt 56 (deux systèmes différents, pas un doublon), appliquée ici à l'admin lui-même.
- **Seule vraie collection partagée entre les deux admins : `sos_alerts`.** Mobile (`admin_sos_page.dart`) et Web (`_SosList` dans `web_admin_dashboard.dart`) lisent/écrivent le même document — les deux peuvent "résoudre" une alerte (`status: 'resolved'`), seul le web a aussi un bouton "Supprimer". Duplication réelle mais bénigne : les deux passent par la même règle `isAdmin()`, aucune divergence de résultat trouvée (un admin qui résout une alerte sur mobile la voit résolue instantanément sur web et inversement, StreamBuilder des deux côtés).

**Phase 2 (sécurité) — deux trouvailles réelles, de gravité très différente :**
- **🟡 "Différence de sécurité mobile/web" confirmée mais moins grave qu'il n'y paraît au premier examen — corrigée par prudence.** `lib/web/admin_auth_service.dart` (`AdminAuthService.signIn()` et le listener `authStateChanges()`) ne vérifiait que l'existence du document `admins/{uid}` — contrairement à `admin_login.dart` (mobile), qui bloque explicitly un sous-admin désactivé (`role=='sub' && isActive==false`) avant même d'afficher le tableau de bord. **Sévérité réelle vérifiée avant de corriger** : `isAdmin()` (`firestore.rules:11-15`) vérifie déjà `isActive` côté serveur pour **toute** lecture/écriture admin — donc un sous-admin désactivé qui se serait connecté sur web via l'ancien code aurait vu un tableau de bord se charger, mais chaque lecture Firestore y aurait échoué (`permission-denied`) : pas une fuite de données réelle, un problème d'expérience/cohérence (l'utilisateur désactivé est laissé entrer dans un dashboard cassé au lieu d'être averti immédiatement, comme sur mobile). **Corrigé** : `AdminAuthService` reproduit désormais exactement la vérification de `admin_login.dart` (nouvelle méthode privée `_isDeactivatedSubAdmin`), appliquée à la fois à `signIn()` (refuse la connexion avec le même message que mobile) et au listener de session (déconnecte automatiquement si le compte est désactivé entre deux sessions).
- **🟢 Trouvaille architecturale plus profonde, documentée mais pas corrigée dans cette passe : le système de `permissions` par section des sous-admins (`admins/{uid}.permissions`, déjà documenté section RBAC) n'est appliqué **nulle part dans `firestore.rules`** — vérifié par recherche exhaustive du mot `permissions` dans le fichier de règles : une seule occurrence, dans un commentaire.** `isAdmin()` ne vérifie que `isActive`, jamais le contenu de `permissions` — ce qui veut dire qu'un sous-admin actif, même avec un tableau `permissions` vide ou restreint à une seule section, a en réalité le **même accès Firestore complet** que n'importe quel autre admin actif pour tout ce qui est gardé par `isAdmin()` (commandes, wallet, commissions, sous-admins…). Le filtrage par `permissions` (`_has(key)` dans `admin_dashboard.dart`) n'est donc qu'une convenance d'interface côté mobile — elle cache des écrans, elle ne restreint aucune donnée réellement. Web aggrave cette même réalité en n'appliquant même pas cette convenance d'interface (les 5 onglets sont visibles à tout admin sans distinction de `permissions`) — mais dans les deux cas, la donnée sous-jacente était déjà également accessible avant et après ce prompt. **Pas corrigé** : construire une vraie application des `permissions` par section dans `firestore.rules` serait un chantier de conception à part entière (modéliser une règle par collection sensible conditionnée sur le contenu du tableau `permissions`), pas une correction ponctuelle — documenté ici pour la première fois comme un vrai gap de moindre-privilège, distinct du bug de connexion ci-dessus qui, lui, est corrigé.
- **🔴 Le vrai bug de cette session, trouvé en vérifiant que les Cloud Functions/règles couvrent bien les actions du site public qui alimentent le Web Admin — les 3 formulaires publics du site vitrine étaient cassés en production.** `firestore.rules` n'avait **aucune règle du tout** pour `driver_applications`/`partner_applications` (aucun `match` bloc, donc refus implicite systématique) ; `contact_messages` avait une règle exigeant `isAuth()` — mais la connexion anonyme automatique est explicitement **« mobile only »** (`lib/main.dart:95-103`, `if (!kIsWeb)`), donc un visiteur du site vitrine public n'est quasiment jamais authentifié. **Conséquence vérifiée dans les 3 fichiers** : `drivers_page.dart` affiche une erreur visible (`SnackBar`) à chaque tentative — donc l'échec était au moins visible côté visiteur — mais `merchants_page.dart` et `contact_page.dart` avalent l'erreur silencieusement (`catch (e) { setState(() => _loading = false); }`, aucun message affiché, `_success` jamais mis à `true`) — un visiteur qui remplit "Devenir partenaire" ou "Contact" ne voit ni succès ni erreur, juste un formulaire qui semble se réinitialiser. **Et même en imaginant l'écriture réussie, la lecture aurait aussi échoué** : `_ApplicationsList` (Web Admin) fait un `.snapshots()` sans règle de lecture sur `driver_applications`/`partner_applications` — l'onglet aurait donc perpétuellement affiché "Aucune entrée pour le moment", indiscernable d'un vrai zéro lead. **C'est exactement la même famille de bug que les 9 bugs financiers déjà trouvés cette session (Prompts 22-49)** : une écriture cross-boundary bloquée par des règles Firestore correctement strictes (ou, ici, simplement absentes), échouant silencieusement en production — sauf que cette fois ce n'est pas de l'argent perdu, c'est l'intégralité du canal de recrutement livreurs/partenaires du site public qui n'a jamais pu fonctionner. **Corrigé** : `firestore.rules` gagne des blocs `driver_applications`/`partner_applications` (création publique avec validation stricte de la forme des champs — nom/téléphone/ville non vides et bornés, `status` doit valoir `'pending'` — lecture/modification/suppression admin uniquement) ; `contact_messages` perd son exigence `isAuth()` (la validation de forme des champs, déjà présente, reste la seule protection — cohérent avec le fait qu'une connexion anonyme est de toute façon gratuite et instantanée pour qui voudrait abuser du formulaire, donc n'apportait aucune vraie résistance à l'abus, seulement une barrière accidentelle contre les vrais visiteurs). Validé par `firebase deploy --only firestore:rules --dry-run` (compilation réussie, aucun déploiement réel effectué).
- **🟢 `password_reset_requests` (5ᵉ onglet web, "Réinitialisation") : vérifié n'être écrit nulle part dans tout le code** (`lib/`, `functions/`) — ni bug de règles, ni bug de connexion : cette fonctionnalité n'a jamais été câblée côté écriture. L'onglet affichera donc toujours "Aucune demande" indéfiniment, pas parce que les demandes échouent, mais parce que rien ne les crée. Distinct du cas ci-dessus (pas une régression, un sous-écran jamais terminé) — pas corrigé (construire le flux de soumission serait une nouvelle fonctionnalité utilisateur, hors périmètre "ne pas refaire l'admin").

**Phase 3 (cohérence) :** aucune divergence de statut/champs trouvée entre les deux admins sur leur seule donnée réellement partagée (`sos_alerts` — même schéma, même valeurs de statut des deux côtés). Aucune donnée visible d'un côté et ignorée de l'autre au sens du prompt (« un admin voit une donnée que l'autre ignore ») au-delà de ce qui est déjà attendu par la Phase 1 (chaque admin a son propre périmètre de collections, sans intersection sauf SOS) — ce n'est pas une incohérence, c'est la conséquence directe de deux périmètres fonctionnels différents.

**Phase 4 (décision) — Option A : les deux admins sont complémentaires, pas dupliqués (à l'exception mineure de `sos_alerts`), aucune fusion ni suppression exécutée.** Le Web Admin n'est pas un « back office » au sens du Prompt 35 (jamais eu vocation à gérer commandes/paiements/boutiques/restaurants/immobilier — cette lecture du Prompt 35 était trop optimiste sur ce que le web couvrait) : c'est un outil de suivi de leads marketing + guichet SOS de secours, un rôle **réellement différent** du Mobile Admin (opérations complètes de la plateforme). Rien à fusionner puisqu'il n'y a presque pas de recouvrement fonctionnel réel. Les deux vrais problèmes trouvés n'étaient pas des problèmes de duplication mais des bugs isolés (connexion web trop permissive pour un sous-admin désactivé ; formulaires publics cassés) — tous deux corrigés dans cette passe, sans toucher à l'architecture à deux admins elle-même.

**Rôle final de chaque admin (à documenter clairement pour la suite) :**
- **Admin Mobile Flutter** : back office opérationnel complet — commandes, wallet, paiements, dispatch, approbation de comptes partenaires/livreurs, zones, sécurité, sous-admins. Le seul à toucher de l'argent ou des comptes utilisateurs réels.
- **Admin Web** : guichet de suivi des leads du site vitrine public (candidatures livreur/partenaire, messages de contact) + alertes SOS (dupliqué avec mobile, sans risque) + un onglet de réinitialisation jamais terminé. Ne touche jamais commandes/wallet/comptes réels.
