## Tests & QA — état réel, honnêteté sur ce chantier

Déjà confirmé (section Sécurité) : **aucun test automatisé n'existe** dans ce projet — `test/widget_test.dart` est un placeholder, `firebase-functions-test` est installée mais jamais utilisée, aucun test de règles Firestore. Le prompt QA demande un programme complet (unitaire/intégration/fonctionnel/sécurité/performance/charge/régression + CI/CD) — construire ça intégralement serait un chantier à part entière, disproportionné à traiter comme sous-effet d'une charte. **Ne jamais prétendre qu'un tel programme existe ou est "fait" tant qu'il n'est pas réellement construit.**

Honnêteté sur la méthode utilisée jusqu'ici pour le chantier AZ IA (M0-M5, mémoire `project_az_ia_integration`) : chaque étape a été vérifiée par chargement Node (`require()` + inspection des exports), démarrage de l'émulateur Firebase Functions, `flutter analyze`, et un test manuel unique du hachage de mot de passe — **pas de tests automatisés persistants**. Du code financier/sécurité sensible (calcul de commission dans `dispatch.js`, transactions wallet dans les outils AZ IA, `hashSecret`/`verifySecret`) tourne aujourd'hui sans aucune couverture de test qui empêcherait une régression silencieuse.

Attente pragmatique à partir de maintenant (pas un programme QA complet, une ligne de base minimale) :
- Toute nouvelle Cloud Function contenant un calcul critique (commission, tarification, remboursement, hachage) devrait s'accompagner d'un test unitaire utilisant `firebase-functions-test` (déjà en dépendance, jamais utilisée) — surtout si demandé explicitement.
- Ne pas construire de pipeline CI/CD, de tests de charge ou de suite E2E sans décision explicite — hors de portée d'une réponse à une charte.
- Si l'utilisateur demande "teste ça", privilégier des tests ciblés sur la logique récemment touchée plutôt qu'une tentative de tout couvrir d'un coup.

**Première suite de tests créée (2026-07-01)** : `functions/test/*.test.js`, exécutable via `npm test` dans `functions/` (`node --test test/*.test.js` — runner natif Node, aucune dépendance ajoutée). Couvre `passwordHash.js` (hachage/vérification), `azia/dispatch.js` (calcul de commission, distance, logique complète d'attribution/broadcast), `azia/pendingActions.js` (création, confirmation, expiration, anti-replay, annulation), `realestate.js` (transitions de visite, permissions, agent approval) — 44 tests, tous verts. Technique clé : les fonctions `onCall(...)` de `firebase-functions/v2/https` exposent une méthode `.run(request)` intégrée au SDK, invocable directement dans un test sans émulateur ni `firebase-functions-test.wrap()` — pattern à réutiliser pour tester d'autres callables. `hashSecret`/`verifySecret` ont été extraites de `functions/index.js` vers `functions/passwordHash.js` pour rester testables sans initialiser Firebase Admin — même chemin à suivre pour toute future logique pure qu'on veut isoler du fichier principal.

**Tests de Firestore Rules ajoutés (2026-07-01) — écrits mais non exécutés.** `rules-tests/firestore.rules.test.js` (nouveau `package.json` racine, dépendance `@firebase/rules-unit-testing`) couvre les patterns les plus sensibles : protection du wallet (`clients`/`livreurs`), state machine `orders`, collections CF-only (`ai_conversations`, `ai_pending_actions`, `audit_logs`, `rate_limits`), séparation super-admin/sous-admin, verrou `pharmacies.password`, la seule règle publique du fichier (`config`). **Ces tests n'ont jamais tourné** : l'émulateur Firestore nécessite Java, absent de cette machine (`java -version` → command not found). Vérifié uniquement par `node -c` (syntaxe) et résolution du module — pas une exécution réelle. Ne pas supposer que ces tests passent tant qu'ils n'ont pas été lancés une fois sur une machine avec Java (ou en CI, où Java est disponible par défaut sur les runners GitHub Actions standard). Commande : `npm run test:rules` à la racine.

**Master Prompt 39 (stratégie QA complète niveau entreprise) — quasi-doublon du Prompt 15, refus reconduit, mais la politique pragmatique déjà actée a été suivie de façon vérifiable tout au long de cette session.** Reconstruire tout le programme demandé (tests widgets, intégration, E2E, charge, pentest sécurité automatisé, rapports QA dans un Back Office) reste disproportionné — même raisonnement qu'au Prompt 15, pas redéveloppé ici. Ce qui est nouveau : la preuve concrète, pas juste l'intention, que « toute nouvelle Cloud Function critique reçoit un test » a bien été respecté. Vérifié précisément (`ls functions/test/` + `npm test`) : **104 tests au 2026-07-02** (était 44 au Prompt 15/22), répartis sur 10 fichiers — 6 de ces 10 fichiers (`authEvents`, `conversationStore`, `fcmTokenCleanup`, `observability`, `orderActions`, `walletReconciliation`) ont été créés **pendant cette session même**, un par Cloud Function critique ajoutée (bugs de paiement corrigés, dispatch, wallet, identité, notifications, mémoire IA) — pas une couverture générale ajoutée après coup, littéralement une conséquence directe de la politique déjà actée. `test/widget_test.dart` reste un placeholder de 7 lignes, inchangé — toujours zéro test Flutter/widget dans `lib/`. Les tests de règles Firestore restent non exécutés localement (Java toujours absent, reconfirmé). `azIaChat` lui-même (la boucle d'orchestration IA) reste sans aucun test automatisé — mocker le client Anthropic serait un chantier à part, déjà noté aux Prompts 31/33, non repris ici.
