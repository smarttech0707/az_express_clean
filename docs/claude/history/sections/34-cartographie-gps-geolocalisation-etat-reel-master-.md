## Cartographie, GPS & Géolocalisation — état réel (Master Prompt 27, 2026-07-02)

Meilleure surprise que prévu sur plusieurs points ; deux gaps totaux confirmés (favoris, géoclôture) ; le reste recoupe des trouvailles déjà actées ailleurs (Livraison, Performance, Multi-pays, Sécurité) — cross-référencées ici plutôt que redupliquées.

**Itinéraires/ETA — bien plus solide qu'on pourrait le croire, MAIS scope limité au suivi actif.** `lib/services/google_routes_service.dart` (`GoogleRoutesService`) appelle réellement l'API Google Directions (distance/durée routières, `duration_in_traffic` si demandé), avec cache mémoire par grille 100 m/TTL 5 min et repli en ligne droite propre si l'API échoue — **jamais que du vol d'oiseau** pour ce chemin-là. Confirmé activement utilisé (pas du code mort) dans `lib/services/realtime_tracking_service.dart`, le service de suivi temps réel pendant une mission active : deux legs calculés (livreur→cible, cible→destination), recalcul throttlé à 120 s + déviation >200 m (cohérent avec la mémoire `project_maps_cost_audit`, qui avait déjà réduit ce throttle de 30 s à 120 s pour maîtriser les coûts — pas un gap, déjà optimisé). **Mais** cette précision routière ne couvre que le *suivi post-attribution* : le moteur de dispatch (`functions/dispatch.js`, voir Prompt 26 ci-dessus) continue de trier les candidats par distance à vol d'oiseau (`haversineMeters`) — c'est un choix assumé pour le coût (appeler Directions pour chaque livreur en ligne à chaque commande serait un multiplicateur de coût direct), pas un oubli, mais ça veut dire que « ne jamais utiliser uniquement le vol d'oiseau » n'est vrai qu'à partir du moment où un livreur est assigné, pas pendant la sélection elle-même.
**Trouvaille annexe — corrigée (2026-07-02).** `lib/services/eta_service.dart` (`ETAService`, distance à vol d'oiseau ÷ vitesse fixe 30 km/h) existait en parallèle de `GoogleRoutesService` sans aucun appelant nulle part dans le code — même famille que `generateAdminOtp()` (Prompt 24). Supprimé (`flutter analyze` toujours clean après suppression).

**Recherche d'adresse — déjà une architecture à 3 niveaux, cohérente avec le reste de l'app.** `lib/services/places_search_service.dart` cherche d'abord dans `places` (Firestore, local), puis Nominatim/OpenStreetMap (gratuit), puis Google Places API seulement en dernier recours si les deux premiers ne suffisent pas — avec cache Nominatim (TTL 5 min). Couvre déjà « recherche par adresse/quartier/ville/point d'intérêt » de façon raisonnable et économe.

**Lieux favoris (Maison/Travail/Famille/Boutique préférée) : gap total, confirmé par recherche exhaustive.** Aucune trace d'adresses enregistrées par utilisateur nulle part dans le code — ni modèle, ni écran, ni champ Firestore. Se recoupe avec la mention déjà actée dans la section AZ IA de ce fichier (préférences opt-in — « adresses favorites » — prévue pour un futur jalon M8, jamais construite).

**Géoclôture (geofencing) : gap total, confirmé par recherche exhaustive.** Aucune détection automatique d'entrée/sortie de zone nulle part (`grep` sur geofenc/proximityAlert/arrivedAt : zéro résultat). Toutes les transitions de statut (`picked_up`, `delivered`) restent des actions manuelles du livreur (bouton), jamais déclenchées par la position GPS elle-même.

**Zones de livraison — gestion géographique réelle, mais sans tarifs/horaires/restrictions par zone.** `admin_zones_page.dart` (déjà documenté section Administration) fait du CRUD complet avec capture GPS — mais confirmé qu'aucun champ tarif/horaire/restriction n'existe sur `zones_livraison`. La tarification reste la formule unique déjà documentée section Livraison (`TarifService`, centrée sur un point GPS fixe) — une zone active/inactive ne change aucun prix.

**Accès aux positions GPS — même trouvaille que Sécurité/RBAC (Prompts 22/24), pas une nouvelle découverte.** Le suivi GPS d'un livreur n'est pas restreint « à une mission active ou aux admins » comme l'exige ce prompt : `livreurs/{id}: allow read: if isAuth();` reste large (voir section Sécurité, chantier explicitement laissé de côté le 2026-07-02).

**Clé Google Maps codée en dur, dupliquée — duplication corrigée (2026-07-02).** La même clé littérale était recopiée telle quelle dans 3 fichiers (`google_routes_service.dart`, `places_search_service.dart`, `places_service.dart`, ce dernier trouvé en vérifiant exhaustivement, pas seulement les deux repérés au premier passage). Centralisée dans `MapsConfig.apiKey` (`lib/constants/app_constants.dart`), les 3 fichiers l'importent désormais au lieu de la redéfinir. **Ne change pas la posture de sécurité** — la clé reste embarquée côté client (exigence du SDK Maps lui-même) ; la restreindre par domaine/app/API reste un changement externe à faire côté Google Cloud Console, déjà noté dans la mémoire `project_maps_cost_audit`, toujours vrai, pas revérifié ici. Ce correctif résout uniquement le problème de duplication (rotation à un seul endroit désormais).

**Hors-ligne, multi-pays, outils admin géographiques (stats)** : déjà couverts respectivement dans Performance (mode dégradé partiel), Multi-pays (vision 10 ans, pas un chantier actuel) et BI/Analytics (`admin_geo_stats_page.dart`, calcul client-side sur les 500 dernières commandes) — pas re-audités ici, juste référencés pour éviter la duplication.
