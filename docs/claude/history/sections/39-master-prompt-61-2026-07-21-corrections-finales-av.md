**Bug Critique #1 — règle `unchanged()` Firestore levait une erreur d'évaluation sur un champ absent d'un côté.** `firestore.rules:36-38` : `unchanged(field)` comparait auparavant par accès direct (`request.resource.data[field] == resource.data[field]`), ce qui lève une erreur d'évaluation Firestore (donc un refus silencieux de l'écriture) dès qu'un champ est absent d'un des deux côtés — même quand le champ réellement modifié n'a aucun rapport. Corrigé en `request.resource.data.get(field, null) == resource.data.get(field, null)` — un champ absent des deux côtés reste "unchanged" (null == null), un champ apparu d'un seul côté est correctement détecté comme changé, et le comportement est strictement identique dans le cas normal (champ présent des deux côtés). Élargissement de sécurité, pas un relâchement : aucune écriture auparavant refusée à raison n'est permise par ce changement. Utilisé par toutes les règles qui en dépendent (ex. `marketplace_products` ligne 509, la branche `orders` du vendeur, etc.).
- Fichier : `firestore.rules`, lignes 26-38.
- Test réel : déployé en production (`firebase deploy --only firestore:rules --project az-express-b0469`) — compilation confirmée sans erreur ; la règle était déjà strictement identique en production avant ce déploiement (« already up to date, skipping upload »), confirmant qu'elle avait déjà été validée lors d'une passe antérieure à cette conversation.

(2) `firestore.rules:551-553` — la règle de création de message vérifiait un champ `senderId` qui n'a jamais existé dans le document réel (`mp_chat_page.dart:198` écrit `senderUid`) ; corrigé pour vérifier `request.resource.data.senderUid == uid()` — ce second bug, plus grave, bloquait silencieusement **tout premier message, indépendamment du bug de regex**.
