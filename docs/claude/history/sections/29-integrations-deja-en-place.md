## Intégrations déjà en place

MTN MoMo / Orange Money / Moov Money / Wave sont **déjà intégrés** via FeexPay comme agrégateur (`functions/index.js`, `feexpayOperatorCode()`) — pas besoin d'intégrations directes séparées sauf limite concrète de FeexPay constatée. Google Maps est intégré (voir mémoire `project_maps_cost_audit` pour le contexte coûts). AZ IA (Claude) est en cours d'intégration (voir `project_az_ia_integration`). Toute nouvelle intégration externe doit garder ses secrets côté `functions/.env` (jamais côté client), suivant le pattern déjà en place pour FeexPay.

**Master Prompt 29 (architecture de paiement universelle multi-fournisseurs) — refusé pour la même raison que les Prompts 23/25 : le prompt redemande une abstraction qui existe déjà, portée par un tiers.** FeexPay **est** déjà l'interface commune demandée — un seul appel API (`initiateFeexPayPayment`) route vers Orange/MTN/Moov/Wave selon `feexpayOperatorCode()`, un seul webhook (`feexPayWebhook`) reçoit les confirmations des quatre opérateurs sous un format unique. Construire une arborescence `payment_core/providers/{orange_money,mtn_momo,wave,cards}/` avec une intégration directe par opérateur dupliquerait ce que FeexPay fait déjà, et nécessiterait en plus des accords marchands séparés avec chaque opérateur (démarche commerciale/légale, pas juste du code) — aucun besoin concret constaté qui justifierait ça aujourd'hui.

Vérifié précisément (au-delà du simple « déjà intégré » déjà su) — le webhook `feexPayWebhook` est plus solide que ce que le prompt pourrait laisser supposer :
- **Authentifié** — par un secret dans l'URL (`?wh_secret=`), pas une signature HMAC (FeexPay ne la supporte pas, déjà noté au Prompt 03). Tentative avec un secret invalide → `security_events` sévérité `high`.
- **Idempotent** — vérifié explicitement (`tx.credited === true || tx.status === 'completed'` → retour immédiat "Déjà traité"), avec en prime une protection anti-rejeu par âge (webhook sur une transaction vieille de >24h → rejeté et journalisé).
- **Statuts internes indépendants du fournisseur** — les statuts FeexPay bruts (`SUCCESSFUL/SUCCESS/COMPLETED/PAID`, `FAILED/CANCELLED/CANCELED/REJECTED`) sont normalisés vers un vocabulaire interne (`completed`/`failed`/`cancelled`/`error`) avant d'être stockés — exactement ce que demande la section Statuts de ce prompt, déjà fait.
- **Journalisé** — `logAudit()` sur chaque crédit réussi, `logSecurityEvent()` sur les tentatives suspectes.
- **Crédit wallet atomique** — dans une transaction Firestore, cohérent avec tout le reste du système.

Écarts réels, distincts de ce qui précède :
- **Remboursement = crédit wallet interne, jamais un remboursement fournisseur.** Vérifié exhaustivement (aucun appel à une API de remboursement/annulation FeexPay nulle part dans `functions/`) : chaque chemin de remboursement du code (annulation, expiration, limite de commandes) crédite le champ `wallet` de l'utilisateur — l'argent ne repart jamais vers l'opérateur Mobile Money d'origine. C'est un choix d'architecture cohérent avec le fait que le Wallet AZ Express est le point de vérité financier de l'app, pas un défaut — mais ça veut dire que « remboursement total/partiel/automatique » de ce prompt ne s'applique qu'à la couche Wallet (déjà documenté section Wallet, Prompt 10/28), jamais à la couche paiement fournisseur.
- **Cartes bancaires** : aucune trace nulle part (recherche exhaustive "card/carte/visa/mastercard" dans `functions/index.js` : zéro résultat) — cohérent avec un marché ivoirien où le Mobile Money domine largement ; pas construit, pas de besoin concret identifié.
- **Conciliation fournisseur** : `walletReconciliationCheck` (Prompt 28, construit ce jour) compare le champ `wallet` à l'historique interne `wallet_transactions` — il ne compare **pas** avec les propres registres de FeexPay (leur API de consultation de statut/historique n'est jamais interrogée après coup). Un webhook perdu (FeexPay confirme un paiement, mais le webhook n'arrive jamais) resterait donc invisible à la conciliation actuelle. Ajouter cette troisième branche (appeler l'API FeexPay pour comparer) serait une extension naturelle de ce qui vient d'être construit, mais c'est une vraie nouvelle intégration externe (pas un ajustement mineur) — à prioriser explicitement, pas supposé inclus dans le travail du Prompt 28.
