## Cloud Functions — architecture & orchestration (état réel, 2026-07-02)

45 Cloud Functions déployées aujourd'hui (`functions/index.js` en est le manifeste — pas un monolithe plat pour autant, voir ci-dessous), région `europe-west1`. Inventaire réel par type (vérifié en comptant les appels, pas supposé) :
- **HTTPS Callable (`onCall`)** : ~17 fonctions — paiements/wallet (`initiateFeexPayPayment`, `initiateWithdrawal`, `payOrderFromWalletCF`, `cancelOrderCF`, `deliverOrderCF`), dispatch (`dispatchOrderToDriver`), auth pharmacie (`pharmacieLogin`, `setPharmaciePassword`, `resetAccountPassword`), admin (`createSubAdmin`, `deleteSubAdmin`), Ekbine (`ekClientConfirmOrder`), AZ IA (`azIaChat`, `aiConfirmAction`), Immobilier (`submitRealEstateAgentRequest`, `approveRealEstateAgentRequest`, `requestPropertyVisit`, `respondToVisitRequest`).
- **HTTPS Request (`onRequest`)** : 1 seule — `feexPayWebhook` (callback externe, ne peut pas être callable).
- **Firestore Triggers** : 12 `onDocumentCreated` + 11 `onDocumentUpdated` — quasi exclusivement des notifications (`notify*`), plus `enforceOrderRateLimit`.
- **Scheduled (`onSchedule`)** : 3 — `autoExpireOrders`, `cleanupExpiredRateLimits`, `aiCleanupExpiredPendingActions`. Pas de Pub/Sub événementiel custom au-delà de ces schedulers.
- **Authentication Triggers** (`beforeUserCreated`/`beforeUserSignedIn`) et **Storage Triggers** : **aucun** — vérifié, zéro occurrence. Pas un oubli : rien dans l'app n'a aujourd'hui de besoin concret (ex. modération d'image à l'upload), donc rien n'a été ajouté par anticipation.

**Organisation réelle — ni un monolithe, ni la structure par domaine complète :** `functions/index.js` reste le manifeste central (helpers partagés `checkRateLimit`/`logAudit`/`logSecurityEvent`/`sendToToken`, + la majorité des triggers de notification, qui sont courts et n'ont pas besoin d'isolation). Mais chaque fois qu'une logique métier critique ou testable a émergé, elle a déjà été extraite dans son propre module, suivant le pattern acté aux Prompts 12/15/22 (« isolée de `index.js` pour rester testable sans initialiser Firebase Admin ») : `functions/passwordHash.js` (hachage), `functions/dispatch.js` (dispatch, réutilisé par AZ IA et le dispatch manuel), `functions/orderActions.js` (paiement/annulation/livraison wallet), `functions/realestate.js` (Immobilier), `functions/azia/` (5 fichiers : `index.js`/`claudeClient.js`/`conversationStore.js`/`pendingActions.js`/`toolRegistry.js`, plus `tools/*.js` par domaine). C'est une organisation **incrémentale et pragmatique**, pas la structure `auth/`/`users/`/`delivery/`/`shopping/`/`marketplace/`/`real_estate/`/`restaurants/`/`pharmacies/`/`wallet/`/`payments/`/`ai/`/`notifications/`/`analytics/`/`admin/`/`security/`/`reports/`/`scheduled/`/`shared/` à 18 dossiers.

**Pourquoi la réorganisation complète en 18 dossiers n'a pas été exécutée :** ce serait déplacer les 45 fonctions déjà déployées, testées et documentées dans une nouvelle arborescence — le même type de changement que le renommage de schéma Firestore (Prompt 21) ou la réécriture complète des règles de sécurité (Prompt 22), tous deux explicitement refusés en exécution silencieuse pour la même raison : risque élevé, bénéfice presque uniquement cosmétique, sur du code de production réel. **Décision actée (2026-07-02)** : adoption **prospective uniquement** — les 45 fonctions existantes ne sont pas migrées ; tout futur module de domaine réellement nouveau (ex. un futur `wallet/` ou `reports/`) peut suivre une forme dossier-par-domaine dès sa création, sans migration rétroactive du code déjà en place. Voir section Méthode de travail.

**Ce qui est demandé mais déjà couvert ou déjà documenté ailleurs comme un chantier séparé** (pas re-audité en détail ici, juste référencé) :
- **Abstraction paiement Orange/MTN/Wave** : déjà faite — FeexPay agrège les 4 opérateurs (`feexpayOperatorCode()`, section Intégrations) derrière une interface commune. Construire une nouvelle couche d'abstraction dupliquerait du code qui fonctionne déjà.
- **Wallet — remboursement, commission, paiement** : déjà exclusivement en Cloud Functions (`initiateFeexPayPayment`/`initiateWithdrawal`/`payOrderFromWalletCF`/`cancelOrderCF`/`deliverOrderCF`, + les outils wallet d'AZ IA). **« Transferts futurs »** (wallet-à-wallet entre utilisateurs) n'existe nulle part — c'est le seul sous-point réellement nouveau de cette section Wallet du prompt, absent de tout audit précédent. **Décision (2026-07-02) : pas construit maintenant** — hors de la feuille de route M0→M8 AZ IA et de tout backlog déjà approuvé ; à reprendre seulement sur priorisation explicite (risque de fraude/anti-blanchiment à concevoir dès le départ si un jour construit — pas un simple CRUD wallet).
- **Marketplace (stock, avis, remboursements)**, **Immobilier (modération, stats)**, **Administration (suspension partenaires, rapports financiers)**, **BI/Analytics (KPI, rapports)**, **Notifications (préférences, diffusion admin)** : chacun déjà documenté comme gap réel dans sa section dédiée (Prompts 07/08/10/11/14 respectivement) — ce prompt les redemande sans changer leur statut ni leur priorité relative.
- **Restaurants/Pharmacies (attribution livreur, suivi, clôture)** : déjà couvert — le dispatch (`dispatchOrderToDriver`) est générique à tous les `type`/`sellerType`, et `deliverOrderCF` (ajouté ce jour) gère déjà la clôture avec crédit partenaire.
- **Auth (validation de compte, gestion des rôles, désactivation)** : RBAC reste par appartenance de collection (voir section RBAC), sans couche `users/` unifiée. La désactivation de compte n'existe que pour les clients (`profil_client.dart`, déjà noté section Sécurité) — étendre ça à livreurs/vendeurs/restaurants/pharmacies serait un vrai chantier neuf, pas encore priorisé.
- **Tests pour chaque fonction + documentation exhaustive par fonction** : contredit directement les décisions déjà actées aux Prompts 15 (base pragmatique : nouvelle CF critique → test dédié, pas 100% de couverture rétroactive) et 19 (commentaires POURQUOI uniquement, pas de docstring systématique) — ce prompt les redemande explicitement mais ça reste un changement de politique à valider, pas une extension silencieuse.

**Master Prompt 25 (API Gateway / microservices / versionnement) — refusé pour les mêmes raisons, déjà actées avant même ce prompt :** ce prompt redemande, presque terme pour terme, ce que la toute première section de ce fichier (« Architecture cible ») a déjà tranché explicitement : *« Il n'y a pas de produit "API Gateway" séparé devant les Cloud Functions — les Cloud Functions callable/HTTP **sont** la couche API. Ne pas introduire de gateway supplémentaire... sans besoin concret. »* Idem pour le versionnement (`/v1/`, déjà refusé section API — conventions : « les callable functions sont déjà versionnées implicitement par déploiement ») et l'enveloppe de réponse unifiée (déjà limitée aux **nouvelles** fonctions uniquement, jamais un retrofit). La chaîne en couches proposée (Controllers → Repositories → Services → API Gateway → Business Services → Cloud Functions → Firestore) ajouterait 3 couches d'indirection supplémentaires entre Flutter et Firestore pour un trafic qui ne le justifie pas aujourd'hui — over-engineering au sens propre, pas juste un chantier repoussé. Côté Flutter, `lib/repositories/`/`lib/services/` existent déjà partiellement (voir Architecture Flutter) ; côté serveur, `functions/azia/tools/*.js` **sont** déjà la couche qui interprète la demande d'AZ IA, applique les règles métier et vérifie les permissions avant tout accès Firestore — c'est exactement l'« AI Service Layer » demandée, juste pas nommée ainsi et pas séparée dans un package à part. AZ IA ne contourne déjà rien : chaque outil passe par `toolRegistry.js`, et toute action sensible par `ai_pending_actions`/`aiConfirmAction` (règle non négociable depuis le début du projet).

**Ce qui est réellement nouveau dans ce prompt, distinct de tout ce qui précède : l'observabilité par requête.** Vérifié directement (aucun `requestId`, aucun middleware, aucun wrapper commun aux 47 Cloud Functions) : `logAudit()` n'est appelé que dans les fonctions où un développeur l'a explicitement ajouté (paiements, wallet, IA, sous-admins, événements d'identité depuis le Prompt 24) — **pas** sur chaque invocation de Cloud Function. Il n'existe donc aucune corrélation systématique requestId↔utilisateur↔durée↔résultat↔erreur permettant de tracer un appel de bout en bout, en dehors de ce que Cloud Logging capture nativement côté infrastructure (non exploité, non recherché depuis l'app). C'est un gap réel et scopé, pas construit silencieusement ici — voir décision ci-dessous.

**Master Prompt 58 (2026-07-03, « Production Monitoring & Observability ») — audit de ce qui existe déjà avant tout ajout, conformément à l'instruction explicite du prompt (« ne pas ajouter de fonctionnalités, ne pas refactoriser, ajouter uniquement les hooks nécessaires »). Verdict : la base est plus solide qu'on pourrait le croire (Crashlytics correctement câblé, AZ IA déjà bien instrumentée, deux mécanismes métier déjà couvrent 2 des 6 événements demandés), mais l'outil générique construit exprès pour ce besoin (Prompt 25) n'a jamais été branché nulle part — la trouvaille la plus significative de cette passe.**

**Phase 1 (inventaire logging) — chaque canal vérifié séparément :**
- **Crashlytics** (`lib/main.dart:80-87`) : déjà correctement configuré, rien à ajouter. `FlutterError.onError = FirebaseCrashlytics.instance.recordFlutterFatalError` (erreurs de framework Flutter) **et** `PlatformDispatcher.instance.onError` (erreurs asynchrones non capturées, pattern officiellement recommandé depuis Flutter 3.3+, remplace l'ancien `runZonedGuarded`) sont tous les deux câblés, mobile uniquement (non supporté sur web, correctement noté). Rien manquant à ce niveau.
- **`audit_logs`/`logAudit()`** : bien alimenté sur les chemins de succès des actions sensibles (paiement, wallet, IA, sous-admins, identité) — déjà documenté (Prompt 25 ci-dessus). **Jamais alimenté sur un chemin d'échec** avant cette passe, à une exception près (`security_events`, qui couvre des scénarios de sécurité spécifiques, pas les échecs métier génériques).
- **`functions/observability.js` (`withObservability`) — trouvaille principale : construit et testé (6 tests, Prompt 25) mais **zéro usage réel**, vérifié par recherche exhaustive de `withObservability(` dans tout `functions/*.js` (seul résultat hors définition/tests : un commentaire dans `azia/index.js`).** La décision actée au Prompt 25 (« appliquer uniquement aux nouvelles fonctions à partir de maintenant ») n'a jamais été suivie dans la pratique — aucune des ~15 Cloud Functions ajoutées depuis (paiements Boutique, Immobilier, sous-admins, nettoyage FCM, conciliation wallet…) ne l'utilise. Conséquence concrète : `request_logs` (la collection que ce wrapper alimente) est vide en dehors de ce qu'écrit la logique bespoke d'AZ IA (voir ci-dessous) — aucune corrélation requestId↔durée↔erreur n'existe pour les Cloud Functions de paiement/wallet/dispatch. **Pas branché dans cette passe** : composer `withObservability` sur les fonctions de paiement déjà en production changerait leur forme de réponse (ajout d'un champ `requestId`) et leur coût (une écriture Firestore de plus par appel) — un changement de comportement réel sur du code financier déjà shippé, pas une simple correction de bug silencieux comme celles déjà faites cette session ; ce n'est pas la décision de l'IA à prendre seule un jour d'audit. **C'est aujourd'hui le levier le plus rentable disponible pour ce prompt** (déjà construit, déjà testé, juste jamais relié) — décision utilisateur à venir plutôt qu'exécution silencieuse.
- **`azIaChat` — déjà le mieux instrumenté de toute la Cloud Functions, vérifié directement (pas supposé).** `functions/azia/index.js:175-188` : `logAiObservability()` est appelée sur le chemin de succès **et** dans le `catch` englobant toute la boucle d'outils, avec `userId`, `toolsUsed`, `turnCount`, `inputTokens`/`outputTokens`, et sur échec `errorCode`/`errorMessage` — exactement le niveau de détail que ce prompt demande en Phase 3 (« contexte, userId, message exploitable »), déjà en place depuis le Prompt 31. Rien à ajouter ici.
- **Catch blocks vides/dangereux** : recherche exhaustive de `catch (_) {}`/`catch (e) {}` (bloc vide) dans `functions/` — **zéro résultat**, confirmant à nouveau la trouvaille déjà actée au Prompt 46 (102 `catch(_) {}` audités côté Flutter, tous délibérés). **Mais un problème plus subtil trouvé, distinct d'un catch vide : deux catch non-vides qui ne remontent l'erreur qu'à `console.error`, jamais à un canal que l'app elle-même lit.** `orderActions.js` — les blocs "création/dispatch de la course de livraison après un achat Boutique déjà payé" (`buildPayBoutiqueOrder` et `buildPayBoutiqueOrderCash`, tous deux `catch (err) { console.error(...); }` sans plus) sont exactement un scénario "commande bloquée"/"livreur introuvable" que ce prompt demande explicitement de savoir détecter (Phase 4) — mais avant cette passe, la seule trace de cet échec était dans les logs bruts Cloud Functions (Cloud Logging), jamais dans `audit_logs`, jamais visible depuis `admin_security_dashboard.dart` ou tout autre écran de l'app. **Corrigé** : les deux catch appellent désormais aussi `logAudit({..., status:'error', targetId: orderId, metadata:{sellerId, error: err.message}})` — même helper déjà injecté et déjà utilisé pour le chemin de succès de ces mêmes fonctions, aucune nouvelle dépendance, aucun changement de la valeur de retour (le client continue de voir `dispatched:false`, comportement inchangé). C'est le seul correctif de code de cette passe — narrow, utilise une infrastructure 100% déjà existante, ne touche à aucune logique métier/financière.

**Phase 3 (Cloud Functions, contexte des erreurs critiques) — état par domaine, pas re-décrit en détail (déjà couvert Phase 1) :**
- **Paiements/wallet** (`orderActions.js`) : succès bien journalisés (`logAudit`) ; échecs de précondition (solde insuffisant, commande non annulable, produit indisponible…) remontent un `HttpsError` visible côté client Flutter mais **n'écrivent jamais nulle part côté admin** — un pic de tentatives de paiement wallet échouées (ex. un bug client qui soumettrait un montant erroné en boucle) resterait invisible sauf lecture manuelle de Cloud Logging. Documenté, pas corrigé (construire un log systématique de chaque précondition échouée toucherait une dizaine de branches `throw new HttpsError(...)` à travers plusieurs fonctions — un changement plus large que le scope "hooks nécessaires" de cette passe).
- **Dispatch** (`dispatch.js`) : déjà couvert par `dispatch_metrics`/`noDriverFoundCount` (Prompt 26/47) — voir Phase 4 ci-dessous, pas re-détaillé ici.
- **AZ IA** : déjà le mieux couvert, voir Phase 1 ci-dessus.

**Phase 4 (alertes métier) — sur les 6 événements demandés, 2 déjà couverts par des mécanismes existants, 2 partiellement (le correctif de cette passe), 2 non couverts et documentés comme tels (pas construits) :**
- **"livreur introuvable" — déjà couvert.** `dispatch_metrics` (écrit par `autoExpireOrders`, Prompt 26) agrège `noDriverFoundCount` par date/zone/tranche de 3h, déjà exploité par un widget dans `admin_security_dashboard.dart` (top 5 zones/créneaux en échec). Rien à ajouter.
- **"wallet incohérent" — déjà couvert.** `walletReconciliationCheck` (scheduler hebdomadaire, Prompt 28) compare le solde réel de 6 collections au solde attendu recalculé depuis `wallet_transactions`, écrit les écarts dans `wallet_reconciliation_findings` (lecture super-admin). Rien à ajouter.
- **"commande bloquée" — partiellement couvert par le correctif de cette passe** (dispatch de livraison Boutique échoué après achat, voir Phase 1) ; le cas générique (une commande reste en `pending`/`broadcast` sans jamais être acceptée ni expirer) est déjà couvert indirectement par `autoExpireOrders` (annule + rembourse après 10 min), qui alimente déjà `dispatch_metrics` — pas un vrai gap supplémentaire.
- **"paiement échoué"** : visible côté client (message d'erreur affiché), jamais agrégé côté admin pour les échecs de précondition wallet (voir Phase 3). Pour FeexPay spécifiquement, déjà bien couvert (`feexPayWebhook` journalise `logSecurityEvent`/`logAudit` sur toute tentative suspecte ou complétée, Prompt 29). **Documenté, pas construit** : un compteur d'échecs de paiement wallet agrégé serait un vrai ajout de fonctionnalité (nouvelle collection ou champ agrégé), explicitement hors du périmètre "hooks nécessaires seulement" de ce prompt.
- **"remboursement échoué"** : même constat que "paiement échoué" — un remboursement qui échoue (précondition non remplie dans `cancelOrderTx`/`refundExpiredBoutiqueOrderCF`) remonte un `HttpsError` client-visible, jamais un signal admin-visible. Documenté, pas construit, même raison.
- **"Cloud Function erreur répétée"** : **aucun mécanisme ne peut détecter ça depuis le code applicatif** — ce type d'alerte (seuil de taux d'erreur sur une fenêtre glissante) est le cas d'usage typique des règles d'alerting **Cloud Monitoring** (console GCP, hors de portée de ce dépôt), pas quelque chose qu'une Cloud Function peut s'auto-surveiller de façon fiable (une fonction qui échoue systématiquement ne peut pas garantir d'exécuter son propre code d'alerte). Documenté comme limite structurelle, pas une omission à corriger en code.

**Phase 5 (performance) — aucun nouveau problème confirmé, cross-référencé plutôt que ré-audité.** Ce terrain a déjà fait l'objet d'audits dédiés et approfondis (Prompts 17/37/42/43/44 : pagination incohérente, absence de Firebase Performance Monitoring, doublons de listeners Firestore `TrackingService`/`RealtimeTrackingService`, fuite mémoire Immobilier déjà corrigée) — la consigne explicite de ce prompt (« corriger seulement les problèmes confirmés ») ne laisse rien à faire ici sans un nouvel angle concret, qu'une repasse superficielle n'aurait pas produit.
