## Design System

Source de vérité : `lib/theme/app_theme.dart`. Il existe déjà un système de tokens complet à réutiliser — ne jamais redéfinir une couleur/taille en dur dans un écran :
- `AppColors` — primaire (orange), secondaire (bleu), succès/erreur/warning, neutres, texte/bordures.
- `AppTypography` — échelle typographique responsive (display/headline/title/body/label).
- `AppLayout` — tailles/espacements responsives (`r()`, `wf()/hf()`, breakpoints `isSmall/isMedium/isLarge`, `xs`–`x3l`, `iconSm`–`iconXl`).
- `AppRadius`, `AppShadow`, `AppTransitions` — rayons, ombres, transitions de page.

**Dette connue à ne pas aggraver :** l'adoption de `AppLayout`/`AppTypography` est inégale (`home_screen.dart` les utilise bien ; d'autres écrans comme `client_wallet_page.dart` ont des valeurs en dur — `fontSize: 46`, `SizedBox(height: 8)`, etc.). Tout nouveau code ou toute modification d'un écran existant doit utiliser les tokens `AppLayout`/`AppTypography`/`AppColors`, jamais des valeurs codées en dur — corriger au passage si l'écran touché en contient déjà, sans en faire un refactor géant non demandé.

**Thème sombre : existe depuis le Master Prompt 120 (2026-07-15)** — `AppTheme.dark`, câblé dans `main.dart` (`darkTheme:`/`themeMode: ThemeMode.system`). Voir la section Master Prompt 120 ci-dessous pour la portée exacte (réel pour toute la chrome Material, pas encore pour les écrans qui lisent `AppColors.xxx` en dur).

**Master Prompt 36 (optimisation Flutter/UX/animations/performance) — recoupe presque entièrement les Prompts 02 (Design System) et 17 (Performance) déjà actés ci-dessus/en section Performance, avec quelques trouvailles précises nouvelles vérifiées directement :**
- **Gestion d'état : 4 `ChangeNotifierProvider` globaux seulement** (`MpProvider`, `MpFavoritesProvider`, `EkProvider`, `AzIaProvider`, tous câblés dans `lib/main.dart`) — le reste de l'app (livraison, wallet, écrans admin, etc.) reste en `StatefulWidget`/`setState`/`StreamBuilder` direct sur Firestore. Ce n'est pas nécessairement un défaut : un état global inutile pour une donnée déjà temps réel via `StreamBuilder` ajouterait de la complexité sans bénéfice — mais ce n'est pas non plus l'architecture « cohérente et unique » que ce prompt suppose ; c'est un mélange délibéré, pas un chantier à unifier sans raison concrete.
- **Skeleton loading : existe déjà, mieux que ce que ce prompt pourrait laisser supposer.** `lib/widgets/glass_kit.dart` a un vrai squelette de chargement avec effet shimmer (`AzShimmerRow` et consorts) ; `mp_product_card.dart` a son propre shimmer local pour les images produit en cours de chargement. Pas un gap — juste pas utilisé partout où un chargement existe encore (`CircularProgressIndicator` brut ailleurs), à uniformiser au cas par cas si un écran est retouché.
- **Hero Animations (transitions à élément partagé liste→détail) : confirmé absent, recherche exhaustive.** Les seules correspondances à « Hero » dans le code sont des widgets privés nommés `_Hero` (bannières de page web), pas le widget `Hero()` de Flutter. Aucune transition à élément partagé nulle part.
- **Accessibilité (lecteurs d'écran) : confirmé absent, recherche exhaustive.** Zéro `Semantics()`, zéro `semanticLabel` explicite dans tout `lib/`. Les widgets Flutter standards (`Text`, `Icon`, boutons) ont un minimum de sémantique automatique, mais aucun étiquetage volontaire n'existe pour les composants plus complexes (cartes personnalisées, `glass_kit.dart`, icônes seules sans texte). Navigation clavier (Flutter Web) non vérifiée séparément — dépend largement du même travail de labellisation.
- **Liens profonds (Deep Links) : confirmé absent côté mobile**, cohérent avec la position déjà actée section Navigation — `main.dart` n'a ni `GoRouter`, ni routes nommées, ni gestion de liens entrants. Le web a `go_router` (qui pourrait en principe les supporter) mais ce n'est pas configuré pour ça aujourd'hui.

Reconstruire/auditer « toute l'application » comme demandé par ce prompt contredirait directement la philosophie déjà actée dans ce fichier (adoption incrémentale des tokens, pas de refactor géant non demandé — voir dette connue ci-dessus) — chacune des trouvailles ci-dessus (Hero animations, accessibilité, liens profonds) est un chantier séparé à prioriser explicitement, pas un sous-effet de cette charte.

**Master Prompt 120 (2026-07-15, « Refonte visuelle premium AZ Express ») — Flutter mobile uniquement (le web, `lib/web/`, garde son propre thème séparé, non touché), zéro changement de logique métier/Firebase. Périmètre validé explicitement avec l'utilisateur (AskUserQuestion) : fondation + composants partagés (`glass_kit.dart`) + les 2 modules à palette dupliquée (Marketplace/Ekbine) — pas une réécriture fichier par fichier des ~116 écrans qui n'ont que quelques couleurs isolées codées en dur.**

- **Palette (`AppColors`, valeurs uniquement, aucun renommage de champ) — propagation automatique à tout consommateur déjà en place** puisque `AppColors` est une classe à membres `static const`. Nouvelle palette douce inspirée de Tailwind slate/orange/green/red/blue/amber : `bg` → `#F8FAFC`, `text` (titre) → `#1E293B`, `textMuted` (texte principal) → `#334155`, `textLight` (texte secondaire) → `#64748B`, `divider`/`border` → `#E2E8F0`, `primary` → `#F97316`, `primaryLight` → `#FB923C`, `primaryDark`/`primaryBg` dérivés du même système (`#EA580C`/`#FFF7ED`, non fournis explicitement par l'utilisateur). `blue` → `#3B82F6` + nouvel alias sémantique `AppColors.info`. **`AppColors.warning` (`#F59E0B`) ajouté — n'existait pas avant cette passe.** `success`/`error` étaient déjà exactement les valeurs demandées, aucun changement nécessaire.
- **Police — Urbanist partout, suppression du branchement SF Pro (iOS) / Poppins (Android-Web).** `AppTypography._build()` et `AppTheme._ts()` utilisent désormais un seul `GoogleFonts.urbanist(...)` inconditionnel (déjà en dépendance, `google_fonts: ^6.1.0`, aucun package ajouté) — `_isApple`/`_sfProDisplay`/`_sfProText` supprimés (code mort). Poids ajustés à la hiérarchie demandée : grand titre Bold 700 (inchangé), titre écran/titre carte SemiBold 600 (`headlineStyle`/`titleLargeStyle`/`TextTheme.titleLarge` passés de w700 à w600), boutons SemiBold 600 (`ElevatedButtonTheme` passé de w700 à w600, `OutlinedButtonTheme` déjà à w600), texte principal/secondaire Regular 400 (déjà corrects, juste la couleur change via la palette). Le poids Medium 500 réservé aux messages AZ IA n'a pas été appliqué globalement (aurait affecté `bodyMedium` partout dans l'app) — laissé pour une prochaine passe scopée à `az_ia_response_widgets.dart`/`az_ia_rich_message.dart`.
- **Rayons & ombres.** `AppRadius` gagne `input`/`inputR` (18px, nouveau, distinct des boutons) et `card`/`cardR` (22px, nouveau, distinct de `xl`=24) ; `btn` reste 20px (déjà exact). `inputDecorationTheme` repointé vers `inputR` (au lieu de `btnR`), `cardTheme`/`dialogTheme` repointés vers `cardR` (au lieu de `xlR`), `glass_kit.dart` (`GlassCard`/`PremiumCard`) idem. Hauteur minimale des boutons `Size(64,52)` → `Size(64,54)` (spec exacte). `AppShadow` (`sm`/`md`/`lg`/`card`/`navFloat`) adouci — alpha/blur réduits pour un rendu "très discret" façon Notion/Airbnb, édité directement sur les listes `BoxShadow` plutôt que sur les constantes `black0X` partagées ailleurs (moins de risque de régression sur des éléments non concernés).
- **Mode sombre — nouveau, n'existait pas du tout avant cette passe.** `AppTheme.light`/`AppTheme.dark` partagent désormais un seul constructeur privé `_build(Brightness)` (évite la duplication) ; nouvelles constantes dark-only sur `AppColors` (`bgDark #0F172A`, `cardDark #1E293B`, `textDark #F8FAFC`, `textMutedDark #CBD5E1`, `textLightDark #94A3B8`, `dividerDark`/`borderDark #334155`) — aucun noir pur. `main.dart` gagne `darkTheme: AppTheme.dark` et `themeMode: ThemeMode.system` (respecte le réglage système par défaut, pas de nouvel écran de préférence/toggle non demandé). **Limite honnête, pas cachée** : ce mode sombre est réel et fonctionnel pour toute la chrome pilotée par `ThemeData` (AppBar, boutons, champs, cartes, dialogs, snackbars, dividers, chips, switch) — tout écran qui utilise les widgets Material par défaut sans surcharge en profite automatiquement. Il ne re-colore PAS les écrans qui lisent `AppColors.xxx` comme des constantes statiques directement dans leur `build()` (la majorité du code aujourd'hui, par conception) — transformer `AppColors` en accesseurs dynamiques (`AppColors.bg(context)`) casserait des centaines d'appels, explicitement le scénario "tout réécrire" écarté par l'utilisateur lors du cadrage de cette passe.
- **`glass_kit.dart` (composant partagé, explicitement dans le périmètre) rendu dark-aware** : `GlassCard` (fill blanc translucide → `Color(0xF21E293B)` en sombre, bordure blanche moins opaque), `PremiumCard` (couleur par défaut `AppColors.card`/`cardDark`, bordure `divider`/`dividerDark`, ombre reprise sur `AppShadow.card`), `AzShimmer` (couleur de fond + intensité du reflet adaptées), `AzDivider` (couleur de ligne adaptée) — tous via `Theme.of(context).brightness`, une poignée de widgets partagés, pas les centaines d'écrans qui les consomment.
- **Marketplace/Ekbine — repointage des 2 modules à palette dupliquée, décision différenciée après vérification.** `lib/marketplace/mp_constants.dart` : `kMpOrange/kMpBg/kMpCard/kMpText/kMpMuted/kMpDivider` repointés intégralement vers `AppColors` (aucune identité de marque distincte trouvée — rafraîchit tout le Marketplace automatiquement). `lib/ekbine/ek_constants.dart` : seuls les tokens neutres (`kEkBg/kEkCard/kEkText/kEkMuted/kEkDivider/kEkOrange`) repointés — **`kEkGreen`/`kEkTeal`/`kEkDark` volontairement laissés inchangés**, vérifié être une vraie identité de sous-marque Ekbine (vert), pas un doublon de l'orange principal ; les repointer aurait re-brandé silencieusement un sous-module sans qu'on le demande.
- **Nettoyage** : suppression de `lib/utils/app_colors.dart` — une **seconde** classe `AppColors` avec une palette différente et non reliée à la vraie, zéro importeur confirmé par recherche exhaustive avant et après suppression, un piège de nom latent pour un futur audit.
- **Icônes (Material Symbols Rounded) — non traité en exhaustif.** Un remplacement `Icons.xxx` → `Icons.xxx_rounded` sur l'ensemble de l'app (centaines d'occurrences) était hors du périmètre validé ; convention à appliquer pour tout nouveau code, pas de renommage rétroactif dans cette passe.
- **Ce qui reste hors périmètre, documenté explicitement plutôt que traité silencieusement** : le build web (`lib/web/`, thème séparé) ; les ~116 écrans avec seulement quelques couleurs isolées codées en dur en dehors de Marketplace/Ekbine (visuellement inchangés jusqu'à une prochaine passe ciblée ou une correction au fil de l'eau) ; aucune capture d'écran avant/après n'a pu être produite (cet environnement ne permet pas d'exécuter l'app sur device/émulateur, limite déjà actée à chaque audit release de cette session).

Vérifié : `flutter analyze` inchangé (8 avertissements préexistants, aucun nouveau sur les 6 fichiers Dart modifiés + 1 supprimé), `flutter test` **16/16**, `flutter build apk --debug` réussi.
